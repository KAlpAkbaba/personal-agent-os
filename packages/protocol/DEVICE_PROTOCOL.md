# Device Protocol v1

Contract between the cloud Device Broker and device agents (first: Windows Device Agent). Both sides validate messages against `packages/schemas/device-protocol.schema.json`. Protocol version is negotiated in `hello`; incompatible versions are rejected at handshake.

## 1. Transport

- WebSocket, **always initiated outbound by the device agent**. No inbound port is ever opened on the device.
- JSON text frames, UTF-8, one protocol message per frame.
- The transport endpoint is configuration, not code: dev `ws://127.0.0.1:8001/v1/devices/connect`; production later `wss://…` over Tailscale (private overlay) without agent code changes. TLS/mTLS termination is a deployment concern below the protocol layer.
- The agent treats any socket failure identically: reconnect with exponential backoff 1 s → 60 s (factor 2, full jitter), forever.

## 2. Identity and enrollment

- Each device generates an **ECDSA P-256 keypair** at first run; the private key never leaves the device (stored under the device account with OS file ACLs; DPAPI hardening is a later milestone).
- Enrollment (REST, one-time):
  1. Owner/operator obtains a one-time enrollment token: `POST /v1/devices/enrollment-tokens` → `{token, expires_at}`. Since M9 this requires an owner bearer session (`Authorization: Bearer <token>`, ADR-0027) **and** a loopback peer.
  2. Agent calls `POST /v1/devices/enroll` with `{token, name, platform, public_key_spki_b64, capabilities}` → `{device_id}`. This is the one broker REST endpoint that does NOT require an owner session: the enrollment token *is* its credential, and the enrolling agent has no owner session by construction. The trust chain still roots in the owner, because only an authenticated owner can mint that token.
  - Tokens are single-use, short-lived (default 15 min), stored hashed.
- In protocol v1, every enrollment creates a **new device identity** (the enroll request carries no device_id, so the broker cannot safely bind it to an existing row). Key rotation for an existing device is deferred to a dedicated authenticated rotate endpoint in a later protocol revision. Revocation: broker marks device revoked; all WS sessions close; the handshake is rejected thereafter; and since M9 every owner session bound to that `device_id` is revoked too, so the device's bearer token stops working on the REST API as well (M9 acceptance: *device revocation invalidates session*).
- Signature encoding: the broker accepts both DER and raw IEEE P1363 `r||s` (64-byte) ECDSA signatures.

## 3. Handshake (over WS)

```
agent  -> {"type":"hello","protocol_version":1,"device_id":"…","software_version":"…","build_id":"…","source_revision":"…","capabilities":["desktop.open_application"]}
broker -> {"type":"challenge","nonce":"<b64 32 bytes>"}
agent  -> {"type":"auth","signature":"<b64 ECDSA-SHA256 over nonce_bytes||device_id_utf8>"}
broker -> {"type":"welcome","session_id":"…","heartbeat_interval_s":10}
```

Failure at any step: broker sends `{"type":"error","error":{"class":"auth_error",…}}` and closes. Unknown/revoked device or bad signature never reveals which check failed.

## 4. Heartbeat and presence

- Agent sends `{"type":"heartbeat","seq":n}` every `heartbeat_interval_s`; broker replies `{"type":"heartbeat_ack","seq":n}`.
- Broker marks the device **offline** when no frame arrives for `2.5 × heartbeat_interval_s`, and on socket close. Presence is observable at `GET /v1/devices`.
- Any frame refreshes liveness; heartbeats are only a floor.
- Since M18.3 a heartbeat MAY carry an optional `status` object (§6g). It is additive, `protocol_version` stays 1, and nothing about presence depends on it: a heartbeat without one is the frame v1 always sent.

## 5. Commands

Broker → agent:

```json
{"type":"command","command":{
  "command_id":"uuid","idempotency_key":"uuid",
  "capability":"desktop.open_application",
  "payload":{"application":"notepad"},
  "expires_at":"2026-08-31T12:00:00Z","trace_id":"…"}}
```

Agent → broker acknowledgements (`command_ack`), monotonic per command:

`accepted` → `running` → terminal `succeeded` | `failed`

```json
{"type":"command_ack","command_id":"…","status":"succeeded",
 "result":{"pid":1234},"error":null}
```

`failed` carries `error: {class, message, retryable}` using the taxonomy of `docs/API_AND_PROTOCOLS.md` (plus `command_expired`, `cancelled`).

Rules:
- **Expiry:** agent rejects a command whose `expires_at` has passed with `command_expired` (never executes). Broker also expires undelivered commands server-side.
- **Idempotency:** agent keeps a persistent map `idempotency_key → terminal ack` (bounded LRU, survives restarts). A duplicate delivery re-sends the recorded terminal ack and never re-executes. Broker dedups REST creation on `idempotency_key` as well. Delivery is therefore at-least-once, execution effectively-once.
- **Cancellation:** broker sends `{"type":"cancel","command_id":"…"}`. If not yet terminal, agent aborts and acks `failed` with `error.class="cancelled"`; if already terminal, it re-sends the terminal ack. A cancel for a command the agent has never seen is acked `failed`/`cancelled` so the broker can settle it (the agent records nothing, having no idempotency key for it).
- **In-flight duplicate delivery:** a duplicate of a command that is still executing is answered with a `running` re-ack and never re-executed (monotonicity preserved).
- **Malformed frames:** receiver answers `{"type":"error","error":{"class":"validation_error",…}}` referencing `command_id` when parseable; the connection stays open.
- **Redelivery:** on (re)connect the broker re-delivers all non-terminal, non-expired commands for that device.

## 5a. Sideband push: `voice_sideband` (M12, ADR-0039)

Broker → agent, additive to v1. Cloud Core's realtime-voice session service delivers
sideband messages for the owner-session companion (`say`, `tool_progress`,
`tool_completed`, `plan_changed`, `narration_cursor`, `leg_closed`) over the SAME
outbound-only device connection, as their own frame type:

```json
{"type":"voice_sideband","session_id":"uuid","event":"tool_completed",
 "payload":{"call_id":"call_1","status":"succeeded","result":{}},
 "at":"2026-09-02T12:00:00Z"}
```

Rules:
- **Opaque to the Device Service.** The service validates the envelope (uuid session id,
  event name, object payload, ≤ 16 KiB serialized) and forwards the frame unchanged over
  the authenticated local IPC (`voice_sideband` pipe frame, carrying the connection id and
  sequence every pipe frame carries). It never interprets the payload, never acts on it,
  and never replies to the broker for it.
- **Nothing from the command path applies:** no `command_ack`, no idempotency key, no
  expiry, no audit row per frame. A frame that cannot be forwarded (no companion
  connected, oversize) is dropped by the agent; Cloud Core already queues undelivered
  pushes on the session record and the client receives the backlog with its next
  `POST /v1/voice/realtime/sessions/{id}/events` response or on `attach`.
- **Older receivers:** an agent that predates this frame answers it with the standard
  `validation_error` error frame (§5, malformed frames); the broker logs that and the
  session continues. Newer agents with no companion connected simply drop it.

## 6. Capability: `desktop.open_application` (M1)

Payload: `{"application":"<name>","args":[…]?}`. The agent maintains a local **allowlist** (default: `notepad`, `calc`, and since 2026-09-09 `mspaint`, so M27's export check can open an image the device itself produced — ADR-0096); anything else fails with `capability_missing`. This route passes `args` to the process unfiltered; `app.launch` (§6i) is the governed spelling of the same act and confines them per application. Nothing in this repository sends `args` here. The application must start in the **interactive owner session** (executed by the session companion, not the background service). Result: `{"pid":<int>,"executable":"<path>"}`.

## 6a. Capability: `desktop.open_artifact` (M3)

Payload: `{"path":"<absolute local file path>","artifact_id":"<uuid>"?}`. The session companion opens the file with its OS-associated application (ShellExecute, never launching a program directly) and returns `{"opened":true,"path":"<canonical path>","handler":"shell-associated"}`. Interactive-session capability, executed by the companion.

Allowlist (checked in order): reject non-absolute/blank/UNC paths (`validation_error`); hard-deny executable extensions even inside a root (`security_scope_error`); require a document extension in the configurable allowlist, default `.pdf .docx .html .htm .txt .md` (`capability_missing`); require the canonical resolved path (symlinks/`..` collapsed) to lie under a configured artifact root, default `%LOCALAPPDATA%\PagentOS\agent\artifacts` plus configured extra roots (`security_scope_error`); require the file to exist (`dependency_unavailable`). Every attempt is written to the companion's local JSONL audit with path, artifact_id and result.

## 6b. Capability family: `browser.*` (M13)

The browser family rides this protocol unchanged — one command envelope, one
`accepted → running → succeeded|failed` lifecycle, one idempotency store, one audit log.
Names, payloads, results, sessions, risk classes and the companion ↔ worker stdio protocol
are specified in **`packages/protocol/BROWSER_CAPABILITIES.md`** (ADR-0050), which is the
binding contract; this section only states how the family is carried on the device side.

- **Advertisement.** The family marker `browser.chrome` and the per-operation names
  (`browser.session_open` … `browser.fetch_evidence`) appear in `hello.capabilities` and in
  the enrollment manifest **only when the device has a configured Browser Worker**:
  service option `BrowserEnabled=true` (written by the installer after the worker's
  self-check passed) and, on the companion, `BrowserWorkerCommand` set. The two desktop
  names are advertised unconditionally, exactly as before. A device never advertises a
  family it cannot execute; Cloud Core selects devices by capability (§8 of the browser
  contract), so an absent name means `no_capable_device`, not a hang.
- **Routing.** The Device Service (Session 0) forwards every `browser.*` command over the
  authenticated companion pipe like `desktop.*`; the Session Companion (owner session)
  hands it to the Browser Worker child process it owns. With `BrowserEnabled=false` the
  service answers `capability_missing` (not retryable) before consulting the companion.
  With no companion connected the answer is `dependency_unavailable` (retryable), as for
  the desktop family. A companion without a configured worker answers `capability_missing`.
  Unknown names in the `browser.` namespace, and the marker `browser.chrome` itself, are
  `capability_missing`.
- **Timeout cap.** The service caps the time one command may hold the companion per family:
  **60 s for `desktop.*`** (unchanged), **120 s for `browser.*`**. The pipe request carries
  `timeout_ms` (the remaining command life clamped to [1 s, cap]) and, since 2026-09-04,
  `deadline_utc_ms` (the absolute Unix-ms moment the service gives up; optional, 0 when
  absent); the companion forwards what is LEFT of that to the worker (less a 500 ms headroom
  so the typed `timeout` arrives before the service synthesises one - measured from the
  deadline, so pipe latency is not charged against the headroom), cancels the worker's
  request when it elapses, and answers `timeout` (retryable).
- **Concurrency.** Browser requests execute concurrently on the companion and their
  responses may interleave on the pipe; `request_id` correlates them, every frame still
  carries the connection id and a strictly increasing sequence (ADR-0028), and one
  `exec_response` answers one `exec_request`. Desktop requests are unaffected.
- **Companion-side checks.** Before a worker result crosses the pipe the companion enforces
  the contract's result cap (48 KiB → `internal_bug`; the worker must truncate) and the
  forbidden-key rule (`cookie`, `authorization`, `set-cookie`, `localstorage`,
  `sessionstorage`, `password`, `token`, `secret`, `apikey` — case-insensitive substring of
  any key at any depth → `security_scope_error`). Error classes outside §8's taxonomy are
  reported as `internal_bug`; `browser_lifecycle_violation` (the worker found, or left, the
  PagentOS profile's Chrome outside its own lifecycle — an orphan holding the profile lock)
  passes through as itself and is **never retryable**, whatever the worker said. The
  worker's stderr goes to the companion log, never into a result.
- **Worker lifecycle.** Started lazily on the first `browser.*` request (or eagerly with
  `BrowserWorkerEager=true`), one at a time; restarted with exponential backoff after an
  exit, with in-flight requests failed `dependency_unavailable` (retryable) immediately;
  pinged for liveness; told `shutdown` and then killed (process tree) when the companion
  stops. **Orphan Chrome (2026-09-03 incident):** whenever the companion kills the worker
  (no hello, missed pings, oversize stdout line, ignored shutdown) or observes it exit, and
  before every worker start, it terminates every `chrome.exe` main process whose command
  line carries `--user-data-dir=<BrowserProfileDir>` — that profile only, never another
  Chrome — logs the pids, and counts them (`OrphanChromesReaped`). The installer's
  `Stop-AgentRuntime` does the same after stopping the worker.
- **Companion log.** The companion logs to its console and to
  `<companion DataDir>\logs\companion.log` (the service's JSONL format, size-bounded and
  rotated): every worker start / exit / kill with its reason, the sanitised worker stderr,
  and one line per browser request (capability, `request_id`, outcome, `duration_ms`).
- **Audit.** The companion writes one `browser_request` row per request — capability,
  `request_id`, outcome class, `duration_ms`, never payload or result text, never a URL —
  plus `browser_worker_started` / `browser_worker_exited` / `browser_chrome_reaped` rows;
  the service writes its usual per-command rows.

Configuration (all `PAGENTOS_AGENT_`-prefixed, nothing machine-specific): service
`BrowserEnabled` (default false); companion `BrowserWorkerCommand`, `BrowserWorkerArgs`,
`BrowserDataDir` (default `<companion DataDir>\browser`), `BrowserProfileDir` (default
`<BrowserDataDir>\profile`), `BrowserChannel` (default `chrome`), `BrowserVisible` (default
true), `BrowserIdleTimeoutS` (default 600), `BrowserWorkerEager` (default false).

## 6c. Capability pair: `desktop.alarm_start` / `desktop.alarm_stop` (M18)

The wake alarm. **Interactive-session capabilities, executed by the Session Companion**: they open a shared-mode render endpoint in the owner's session, which the Session-0 Device Service cannot do and never attempts. The service routes them over the companion pipe like `desktop.open_*`, under the same 60 s per-command cap — `alarm_start` arms a ramp and returns, it does not hold the pipe while the alarm rings.

Both names are advertised **unconditionally**. A companion with no render endpoint answers `dependency_unavailable` (retryable) — a true statement about right now, not a claim that the device cannot ring — and a companion built without an alarm controller answers `capability_missing`. Neither ever hangs.

`desktop.alarm_start`

Payload: `{"alarm_id":"<id>"?, "label":"<short text>"?, "wake_volume":{"start":<0..1>,"end":<0..1>,"ramp_seconds":<int>}?, "max_duration_s":<int>?}`
Result: `{"started":true,"alarm_id":"…","start_volume":<f>,"end_volume":<f>,"ramp_seconds":<i>,"max_duration_s":<i>,"end_volume_clamped":<bool>,"ramp_seconds_clamped":<bool>,"replaced_alarm_id":"…"|null}`

`desktop.alarm_stop`

Payload: `{"alarm_id":"<id>"?}` — omit it to stop whatever is ringing.
Result: `{"stopped":<bool>,"alarm_id":"…"|null,"was_ringing":<bool>}`

Rules, all enforced on the device regardless of what Cloud Core validated (a routine row written before a validator existed must not ring at full volume today):

- **A wake volume is a RAMP, never a level.** `start` defaults to 0.05, `end` to 0.8, `ramp_seconds` to 60. A `start` at or above **0.5** is refused with `validation_error` — a caller asking to begin at 0.9 is not asking for a ramp, and quietly lowering it would hide a malformed request. `start > end` is refused for the same reason.
- **There is a ceiling, and clamps are reported.** An `end` above **0.85** is clamped to it and `end_volume_clamped` says so; a `ramp_seconds` below 5 (or above 3600) is clamped into range and `ramp_seconds_clamped` says so. Clamping rather than refusing here keeps the alarm ringing at a safe level instead of not ringing at all, and the result carries the number it will actually reach.
- **The level scales the companion's own generated samples.** Nothing in this capability touches the Windows master volume or the endpoint's volume: an alarm that raised the system mixer would leave the machine loud after it stopped, and would do it to every other application at once.
- **It always stops.** Three ways: `desktop.alarm_stop`, the alarm's own `max_duration_s` (default 300 s, clamped to 10–1800 s, checked continuously), and companion shutdown. No ringing alarm outlives the companion process.
- **`alarm_stop` is idempotent.** Stopping an alarm that already stopped is a success with `was_ringing:false`. A stop naming a *different* alarm than the one ringing does nothing and reports `stopped:false`, so a stale retry cannot silence the alarm that replaced it.
- **One alarm at a time.** A second `alarm_start` stops the first and names it in `replaced_alarm_id` rather than layering two ramps on one endpoint.
- **Since M18.3, both names consume a local arm** (§6f) carrying the same `alarm_id`: a successful `alarm_start` because the cloud got there in time, and a successful `alarm_stop` because the owner has already dealt with it. That is what makes "the fallback never doubles the cloud's alarm" true rather than likely.

Configuration (companion, `PAGENTOS_AGENT_`-prefixed): `AlarmRenderDevice` (id or name substring; falls back to `VoiceRenderDevice`, then the session's default render endpoint, resolved per alarm so a headset plugged in after startup is usable).

## 6d. Capability: `desktop.display_off` — the invariants (M18)

Turns the owner's display off, and nothing else. **Interactive-session capability, executed by the Session Companion** — a `WM_SYSCOMMAND` / `SC_MONITORPOWER` broadcast from Session 0 reaches no window the owner can see. Sent with `SendMessageTimeout` (2 s, `SMTO_ABORTIFHUNG`), because a single hung top-level window would otherwise stall the companion forever; a timed-out broadcast is reported as `dependency_unavailable`, never as success.

> **Payload, result and the third gate are in §6e** (M18.3). This section keeps the invariants,
> which have not changed; §6e adds `holdoff_s`, the refusal shape, the observed state and the
> monitor list.

- **Off is the only operation.** M18 v1 does not shut down, reboot, hibernate, suspend or log off on any inference (`docs/M18_HOLOGRAPHIC_CORE_SPEC.md` §4, `docs/M18_THREAT_MODEL.md` §5). Turning a display off is undone by moving the mouse; suspending a machine that is mid-research is not, and the background work would stop with it. A test reads the implementation source and fails if a shutdown/suspend API name appears in it, so the capability cannot quietly grow a second meaning.
- **Two independent gates, and neither knows about the other.** On the device, the name is advertised and routed only when `DisplayPowerEnabled` is set (default false) — service and companion each refuse it otherwise with `capability_missing`, so a command aimed straight at the device still cannot blank the screen. In Cloud Core, a routine's `display_action` is refused before it ever becomes a command, until display-off has passed its own owner qualification (`docs/M18_HOLOGRAPHIC_CORE_SPEC.md` §7). A single flag flipped by accident is therefore not enough to interrupt unrelated owner work.
- A device with the flag off does not advertise the name, so Cloud Core's capability selection reports `no_capable_device` rather than reaching a device that lied about what it can do.

Configuration: `PAGENTOS_AGENT_DisplayPowerEnabled` on both the Device Service (routing + advertisement) and the Session Companion (execution + advertisement).

## 6e. Capability family: `desktop.display_wake` / `desktop.display_status` / `desktop.display_off` (M18.3)

The display family. All three are **interactive-session capabilities executed by the Session Companion**, under the desktop family's 60 s per-command cap. `display_wake` and `display_status` are advertised **unconditionally**; `display_off` keeps both gates of §6d and gains a third that is not a flag.

### `desktop.display_wake`

Payload: `{"reason":"<short token>"?}`
Result: `{"woken":true,"method":"display_needed+pointer_move_zero","observed_state":"unknown"|"off"|"on"|"dimmed","observed_at":"<iso-8601>"|null,"input_idle_s":<number>|null}`

Two steps, in this order: a **momentary** `SetThreadExecutionState(ES_DISPLAY_REQUIRED)` — never `ES_CONTINUOUS`, because a standing claim nobody clears is indistinguishable from a broken power plan — then a zero-delta pointer move (`SendInput`, `MOUSEEVENTF_MOVE`, `dx = dy = 0`). **Never a key event.** The synthetic-input structure the companion declares has a pointer member and no keyboard member, so there is nothing to fill in even by mistake, and a structural test fails if any keyboard API name appears in a display source file. Advertised unconditionally: waking a screen is the exact inverse of the one operation that takes something away.

### `desktop.display_status`

Payload: `{}`
Result: `{"observed_state":"unknown"|"off"|"on"|"dimmed","observed_at":"<iso-8601>"|null,"input_idle_s":<number>|null,"monitors":[{"index":<i>,"primary":<bool>,"left":<i>,"top":<i>,"width":<i>,"height":<i>}]?}`

- **Observed, never inferred.** The companion runs a message-only window registered for `GUID_CONSOLE_DISPLAY_STATE` (0 off, 1 on, 2 dimmed) and `GUID_MONITOR_POWER_ON` (0 off, 1 on); the state is the last value it was handed, with the moment it arrived. Before the first notification the answer is `unknown` with a null `observed_at`, and it stays `unknown` — a device that guessed "on" from a recent keystroke would be reporting the idle timer twice under two names. Windows offers no reliable synchronous "is the display on?" call, and the ones that look like it are the same APIs that turn a display off, so the observer holds no way of driving a display at all.
- **`monitors` is reporting only.** From `EnumDisplayMonitors`; **absent** (not empty) when the session could not enumerate them, because "could not tell" and "this machine has no monitors" are different claims. M18.3 changes no topology, resolution, orientation or primary-monitor choice, and a structural test fails if a display-configuration API name appears.
- **`input_idle_s` is `null` when unknown**, which is a different statement from `0`.

### `desktop.display_off` (changed in M18.3)

Payload: `{"reason":"<short token>"?,"holdoff_s":<int>?}` — `holdoff_s` defaults to **120**, clamped to 0…3600. A non-integer `holdoff_s` is a `validation_error`; an out-of-range one is clamped, because an absurd number still describes an intent while a non-number does not.

Result on a **refusal**, which is a **successful** `command_ack` and not an error:

```json
{"display_off":false,"refused":"recent_input"|"alarm_active",
 "input_idle_s":<number>|null,"holdoff_s":<int>,
 "observed_state":"…","observed_at":"…"|null}
```

Result on a real off:

```json
{"display_off":true,"method":"wm_syscommand_monitorpower",
 "input_idle_s":<number>|null,"holdoff_s":<int>,
 "observed_state":"…","observed_at":"…"|null,"monitors":[{…}]?}
```

- **Why a refusal is a success.** Nothing failed: the device looked, and the answer was no. An error class here would make a correct refusal indistinguishable from a broken device, and the caller would retry it.
- **`recent_input`** when the idle time is known and strictly less than `holdoff_s`. 120 s of quiet is enough; 119.9 s is not. An **unknown** idle never satisfies the holdoff by itself and never blocks the off either — the device does not fabricate a zero (refuse forever) or a large value (claim quiet it never observed).
- **`alarm_active`** whenever an alarm is ringing, checked first and whatever the idle timer says. Three hours of quiet is exactly the state a wake alarm fires into; darkening the screen at that moment is the machine working against the thing it just did.
- **The observed state on a successful off is read back after the broadcast**, so a broadcast nothing honoured cannot be reported as a dark screen. It may still be `unknown` on a device that was never told.
- The two gates of §6d are unchanged and are checked first: with `DisplayPowerEnabled=false` the answer is `capability_missing` (not a refusal result), from the service before the companion is consulted and from the companion again.

## 6f. Capability pair: `desktop.alarm_arm` / `desktop.alarm_disarm` (M18.3)

The **local fallback** for an alarm the cloud intends to ring. A wake alarm that only rings when the cloud can reach the device is not a wake alarm; it is a wake alarm plus an availability requirement the owner never agreed to. So when Cloud Core schedules a wake-up it also ARMS the device. Both names are advertised unconditionally; the companion persists arms at `%LOCALAPPDATA%\PagentOS\companion\armed-alarms.json` (owner profile, not the service's machine tree), written atomically by write-then-move.

`desktop.alarm_arm`

Payload: `{"alarm_id":"<id>","fire_at":"<iso-8601>","grace_s":<int>?,"label":"<text>"?,"wake_volume":{…}?,"max_duration_s":<int>?}`
Result: `{"armed":true,"alarm_id":"…","fire_at":"…","grace_s":<i>,"fire_local_at":"…","replaced":<bool>,"armed_count":<i>}`

`desktop.alarm_disarm`

Payload: `{"alarm_id":"<id>"?}` — omit it to forget every arm.
Result: `{"disarmed":true,"alarm_id":"…"|null,"was_armed":<bool>,"armed_count":<i>}`

- **`alarm_id` is required to arm.** Unlike `alarm_start`, an anonymous arm could never be consumed by anything except its own firing.
- **`grace_s` defaults to 60**, clamped to 0…3600. The device rings at `fire_at + grace_s`, not at `fire_at`: firing at exactly `fire_at` would race the cloud's own command over a link with any latency at all, and the owner would sometimes hear two alarms.
- **One ring per `alarm_id`, always.** Three things consume an arm, each removing it from the store first: a `desktop.alarm_start` naming that id (the ordinary case — the cloud got there in time), a `desktop.alarm_stop` naming it (the owner has already dealt with it), and `desktop.alarm_disarm`. Firing locally removes it too, **persisted before the first sample is generated**, so a companion that dies mid-ring gives the owner a missed alarm — which they notice — rather than a second one on the next start.
- **Arming is idempotent by `alarm_id`**: the same id replaces the existing arm and says so in `replaced`. Disarming is idempotent the way `alarm_stop` is: disarming something never armed is a success with `was_armed:false`.
- **Reload on start is conservative.** An arm whose local fire time already passed rings **once** if it passed less than **2 hours** ago, and is **expired with an audit row** otherwise. Waking someone twenty minutes late is a late alarm; waking them at 14:00 for a 06:30 alarm is a machine behaving badly.
- **The fallback rings the same alarm.** `label`, `wake_volume` and `max_duration_s` are carried into the `alarm_start` path of §6c, so the local ring obeys the same ramp, the same ceiling and the same `max_duration_s`. With no render endpoint the failure is audited once per arm, not once per tick.
- Audit rows: `alarm_arm`, `alarm_disarm`, `alarm_arm_consumed`, `alarm_arm_fired`, `alarm_arm_expired`, `alarm_arm_ring_failed`.

Configuration (companion): `PAGENTOS_AGENT_ArmedAlarmStorePath` overrides the default path.

## 6g. Capability: `desktop.activity_status`, and the heartbeat's `status` (M18.3)

Payload: `{}`
Result — and, verbatim, the optional `status` object on a heartbeat:

```json
{"input_idle_s":<number>|null,
 "display_state":"unknown"|"off"|"on"|"dimmed",
 "display_observed_at":"<iso-8601>"|null,
 "alarm_ringing":<bool>,"ringing_alarm_id":"…"|null,
 "armed_alarms":<int>,"next_alarm_at":"<iso-8601>"|null}
```

- **One shape, one producer.** The heartbeat's `status` IS this capability's result. A status assembled separately from the capability's answer would drift, and the version Cloud Core reasons about most often would be the one nothing tests.
- **`input_idle_s` comes from `GetLastInputInfo` — a tick count and nothing else.** No key, character, pointer position, window title or application name is ever read, stored or sent. A structural test fails if a hook, key-state, raw-input or foreground-window API name appears in the companion's input source.
- **It reports; it does not decide.** There is no "the owner is asleep" field and there will not be one. The inference from idle time and display state to a person's state belongs where it can be explained, argued with and turned off — in Cloud Core, against the presence model (`docs/M18_THREAT_MODEL.md` §4).
- **On the heartbeat the field is OPTIONAL and additive; `protocol_version` stays 1.** The Device Service asks the companion for `desktop.activity_status` before each heartbeat and attaches the answer. Absent means "not known", never "nothing is happening": no companion connected, a companion that did not answer within **1.5 s**, a companion that threw, or an agent older than the field all produce a heartbeat without `status`, byte-for-byte the frame v1 always sent. Presence and liveness never depend on it — a status path that could stall a heartbeat would let a busy companion make the device look offline, which is strictly worse.
- **The key set is closed and the SERVICE closes it.** `additionalProperties: false` inside `status` means one unknown key would fail the broker's validation for the whole heartbeat, so the Device Service projects the companion's answer onto exactly the seven keys above before sending. A newer companion cannot break an older service's connection.

## 6h. Capability: `desktop.play_audio` (M18.3)

Plays ONE short piece of audio the owner's own broker rendered — a spoken greeting after a wake alarm — in the owner's interactive session. Advertised unconditionally; **interactive-session capability, executed by the Session Companion**, under the desktop family's 60 s cap, and it **blocks until the audio has finished** so a caller sequencing "ring, then greet" gets an honest completion.

Payload: `{"audio_id":"<id>","audio":{"url":"<https://broker/…>","sha256":"<64 hex>","bytes":<int ≤ 2097152>,"format":"wav"},"level":<0..1>?,"max_seconds":<int ≤ 20>?}`
Result: `{"played":true,"audio_id":"…","duration_ms":<int>,"level":<f>}`

Four bounds, all checked on the device:

- **Origin.** The **Device Service** refuses the command with `security_scope_error` (never retryable) before it reaches the pipe unless the URL's scheme, host and port equal the broker REST origin this device is configured for. A device with no configured broker origin refuses every `play_audio`: "we could not tell where audio may come from" and "this audio may be played" must not be the same answer. The same host on a different port is a different server.
- **Size.** `bytes` must be 1…2 MiB, and the bound is enforced **while reading** (a `Content-Length` is a claim). A body that differs from the declared size is a `validation_error`.
- **Digest.** The SHA-256 of the bytes that arrived must equal `audio.sha256`. A mismatch is `security_scope_error`, **not retryable**: what is at that URL is not what Cloud Core described, and fetching it again would not change that.
- **Duration and level.** `max_seconds` defaults to 20 and is clamped to 1…20; audio longer than that is **trimmed rather than refused**, because the owner asked to be greeted and a slightly short greeting serves that better than silence plus an error. `level` defaults to **0.75**, clamped to 0…1, and **scales the samples** — nothing in this capability touches the Windows master or endpoint volume, and a structural test fails if any endpoint-volume API name appears in any companion source.

Other rules: the fetch has a **10 s** timeout (`timeout`, retryable); a non-2xx answer is `dependency_unavailable` (retryable); the container must be RIFF/WAVE **PCM16**, mono or stereo, 8 000…192 000 Hz — anything else is a `validation_error` rather than a best-effort guess. The render endpoint is opened at the **WAV's own rate and channel count** and the shared-mode render path converts to the endpoint's mix format; there is no resampler in the agent. With no render endpoint the answer is `dependency_unavailable` (retryable), as for the alarm.

## 6i. Capability family: the Digital Operator (M19)

The operator family rides this protocol unchanged — one command envelope, one lifecycle, one idempotency store, one audit log. The binding specification is **`docs/M19_DIGITAL_OPERATOR_SPEC.md`** (ADR-0082); this section states how the family is carried on the device side and what the companion guarantees.

**Names** (`AgentCapabilities.Operator`, 32, no family marker — every name is an operation):
`app.launch`, `app.list`, `app.activate`, `app.close`; `window.list`, `window.current`, `window.activate`, `window.minimize`, `window.maximize`, `window.restore`, `window.move`, `window.resize`, `window.close`; `keyboard.type`, `keyboard.key`, `keyboard.shortcut`; `pointer.move`, `pointer.click`, `pointer.double_click`, `pointer.right_click`, `pointer.scroll`; `ui.inspect`, `ui.invoke`, `ui.set_value`, `ui.select`; `screen.capture`, `screen.inspect`; `file.open`, `file.reveal`; `terminal.open`, `terminal.execute`, `terminal.status`.

- **Advertisement.** The family appears in `hello.capabilities` and the enrollment manifest **only when `OperatorEnabled=true`** on the service (the installer's `-Operator` switch; the `capabilities` verb reports `operator_enabled`) AND on the companion (`PAGENTOS_AGENT_OperatorEnabled=true`, which is what builds the operator object at all). Order in the manifest: desktop, alarm, ambient, display, browser, operator — an append, never a reshuffle.
- **Routing.** Every name is interactive (`AgentCapabilities.IsInteractive`): the Device Service (Session 0) forwards it over the authenticated companion pipe and never touches a window itself. With `OperatorEnabled=false` the service answers `capability_missing` (not retryable) before the pipe; a companion without the operator answers the same; no companion connected is `dependency_unavailable` (retryable), as for every family. There is no other path to the desktop: no REST route, no script, no worker.
- **Caps and budget.** The service caps one command at **30 s** for the family and **15 s for `app.launch`** (a 10 s window wait plus headroom). The pipe request carries `timeout_ms` and `deadline_utc_ms` as for the browser family; the companion budgets what is LEFT less the same 500 ms headroom, cancels the action when it elapses and answers `timeout` (retryable). A cancelled command answers `cancelled`. Operator requests run on the companion's concurrent (long-running) path so the heartbeat's status request is never behind a launch — but the operator itself executes **one action at a time** (one pair of hands).
- **Every result carries `observed: {…}`** — a fresh read AFTER acting: the re-read window (`window_id, pid, image, title, state, rect{x,y,width,height}, foreground, class_name, owned`), the value read back, the process still alive, the cursor, the selection. A window action whose re-observed state is not the requested one (`window.maximize` observed `normal`, `window.move` off by more than **8 px**) fails with **`postcondition_failed`** (retryable) instead of succeeding on the strength of the call having returned. `app.activate` / `window.activate` verify `GetForegroundWindow` after up to 3 attempts.
- **`window_id`** is `w-<hwnd>-<tick at first sight>`, issued by the companion's registry the first time it sees a window and stable until that handle is gone. An id the registry never issued — a made-up one, one from a previous companion life — is `ui_target_not_found` (retryable): observe again and re-resolve. Handles never cross the pipe on their own.
- **The focus guard (spec §1, invariant 2).** Immediately before any `keyboard.*` or `pointer.*` event the companion compares the payload's window — handle, pid, image and the first 24 characters of the title, all freshly read — with the actual foreground window. A mismatch is **`focus_mismatch`** (retryable) naming both windows; nothing is sent, and the companion never activates the target on its own — activation is `window.activate`, an observable action the planner asks for. **During a keyboard stream the guard is asked again before EVERY batch** (64 events = 32 characters, 5 ms apart; ADR-0082 addendum 2 finding 2) — identity only (handle, pid, image; the title changes because of the typing, Notepad prefixes `*`). A "no" stops the stream: `focus_mismatch` (retryable) whose message carries `typed_chars=<n>` (characters handed to the system while the target was verified in front), `confirmed_chars` (all but the last batch) and `uncertain_chars` (that last batch — Windows assigns injected input to the thread that retrieves it, so a batch handed over within one pause of the change can reach the window now in front; the lab measured exactly one batch doing so). Nothing is sent after the change. The planner reads the target back (`ui.inspect`) before continuing from `confirmed_chars`.
- **Payload validation, before anything touches a window.** Required fields and types; `text`/`value` ≤ **4096** chars with no control characters except tab and newline; **`secret: true` is refused with `validation_error` "secrets are never typed"** on `keyboard.type` and `ui.set_value`; `key` from the fixed list (`enter escape tab backspace delete insert home end pageup pagedown up down left right space f1..f12`); `keys` = 1–3 of `ctrl alt shift` plus exactly one key (a letter, a digit or a named key) — `win` is not offered; pointer `x,y` inside the window (`space: "window"`, the default) or inside the virtual screen (`space: "screen"`), `delta` in ±50 notches and non-zero; `depth` ≤ 5 and `max_nodes` ≤ 200 on `ui.inspect`; `timeout_s` ≤ 30 on `terminal.execute`. Every result passes the browser family's forbidden-key scan (`cookie authorization setcookie localstorage sessionstorage password token secret apikey`, normalised substring, any depth) before it leaves the companion → `security_scope_error`; a UI element that says it is a password field is described as `masked: true` and its value is never read.
- **`app.launch`** takes an allowlisted name (`notepad`, `calc`, `mspaint`, `explorer`, `powershell`, `chrome`, `msedge`), an absolute `.exe` under Program Files / Windows, or — since 2026-09-09, ADR-0098 — **an application this system built**: an absolute `.exe` whose RESOLVED path lies inside the RESOLVED native root (§6n). Anything else is `permission_denied`. The native-root form is resolve-then-contain rather than a prefix compare, because unlike Program Files that root is owner-writable: a junction planted inside it is followed before the comparison, and `native2` is not under `native`. It widens no trust the family does not already hold — an `.exe` reaches the native root by exactly one route, `dotnet publish`, and the sibling of that command, `dotnet test`, already RUNS code compiled from the same scaffolded source, while `project.scaffold(root:"native")` itself writes text only and refuses every launcher extension. It exists because without it a factory can produce an application nothing can start: on the owner's machine the item-28 qualification built a real EXE and was refused twice, correctly — `file.open` opens documents, and `app.launch` knew only Program Files. **`args` are policed per application** (ADR-0082 addendum 2 finding 3): `notepad`, `explorer` and `mspaint` take at most one argument, an absolute path that resolves inside the authorised roots (passed on in its resolved form); `calc`, `powershell` (the governed path is `terminal.execute`), an absolute `.exe` path and any other name take none; `chrome` and `msedge` take only `http://` / `https://` URLs (absolute, with a host, no whitespace) and `--new-window`. Anything else — `--remote-debugging-port`, `--load-extension`, `--disable-web-security`, `--user-data-dir`, `--proxy-server`, `--headless`, `-Command`, `file://`, `javascript:`, a bare host — is `validation_error` naming the argument, before a process exists. `file.open` with `application` puts its one argument (the resolved path) through the same policy, so `file.open` into `calc`, `powershell` or a browser is refused. It waits ≤ 10 s for a top-level window of the new pid and answers `{pid, window_id|null, title|null, executable, observed:{window_appeared, window, process_alive}}`. **`app.close`** posts WM_CLOSE to the process's windows and waits ≤ 5 s; a dialog that appears meanwhile (an owned window or a `#32770` of that pid) stops the wait early and is reported as `closed:false, modal:{window_id, window, dialog:{title, buttons:[…], texts:[…]}}` described through UI Automation, so the planner can `ui.invoke` the right button by name; a process still alive after the wait is reported, not killed, unless `force:true` (then `method:"terminated"`). `window.close` behaves the same for one window.
- **`ui.*`** run over `System.Windows.Automation` (the Windows Desktop runtime's UIAutomationClient, referenced directly; the companion stays a console process). Elements are `{automation_id, name, control_type, class_name, enabled, bounds{x,y,width,height}|null, value?, masked?, selected?, toggle_state?, children}`; an element is named by `automation_id`, `name`, `name_prefix` (optionally with `control_type`), and `ui.inspect` may start at such an element. `ui.invoke` uses Invoke, else Toggle, else SelectionItem, else ExpandCollapse. `ui.set_value` uses the Value pattern, else — for a native text window that exposes only the Text pattern (classic Notepad's multi-line edit is such a Document) — `WM_SETTEXT` to that window; either way the value is **read back** and reported as `observed_value`. `ui.select` selects the named child item and reports the container's selection read back.
- **`screen.capture`** is `PrintWindow` of one window or `BitBlt` of the primary screen, PNG-encoded by a small managed encoder (no `System.Drawing`), `{width, height, png_base64, bytes, scale}`; over **2 MiB** it is halved (scale 2, then 4) and refused if still over; nothing is written to disk. **`screen.inspect`** is `{monitors:[…], virtual_screen, foreground, cursor}`.
- **`file.open` / `file.reveal`** accept only an absolute path inside the owner's authorised roots (`OperatorRoots`, default Documents, Desktop, Downloads, Pictures, Videos, Music and the operator fixture root `%TEMP%\pagentos-operator-fixture` — NOT the profile directory, so AppData and `.ssh` are out by default). **The rule is resolve-then-contain** (ADR-0082 addendum 2 finding 1): the path is opened and the file system asked what it really opened (`GetFinalPathNameByHandle`, every junction, mount point and symbolic link in every component followed), and only that final path is compared with the roots' own final paths (a root may itself be a junction). A junction inside a root pointing outside it resolves to the outside and is `permission_denied`; a path that cannot be resolved (missing, unreadable) is `permission_denied` too — there is no lexical fallback; an executable extension on `file.open` likewise. The companion acts on the RESOLVED path and reports it. `file.open` with `application` launches the allowlisted app on the path (under that app's argument policy); without it, ShellExecute. `file.reveal` runs `explorer.exe /select,<path>`, waits for the new Explorer window and reports the list's selection read back (`observed.selection`).
- **The terminal is an allowlist** (`TerminalAllowlist`, default `hostname`, `whoami`, `ipconfig`, `Get-Date`, `Get-ComputerInfo -Property *`, `Get-Process -Name *`, `Get-ChildItem <path>`; `*` = one token of anything, `<path>` = one absolute path that RESOLVES under an authorised root (the same resolve-then-contain rule as `file.*`: a junction out of the root, or a path that does not exist, does not match), token counts must agree). A command carrying `; | & $ ( ) { } < > \`` or a newline, or not matching a pattern token for token, is **`permission_denied` before a process exists**. What runs, runs headless — `powershell.exe -NoProfile -NonInteractive -Command`, no window, output UTF-8, System32 first on the child's PATH so an allowlisted name resolves to the system binary — with a hard timeout (`timeout_s`, default and maximum 30 s; the process tree is ended on timeout and on cancel), and answers `{exit_code, stdout, stderr, duration_ms, truncated, matched}` (output bounded at 32 KiB). `terminal.open` opens a visible PowerShell window (`{pid, window_id}`); `terminal.status {pid}` answers `{alive, exit_code?}`.
- **Audit and log.** One `operator_request` row per request — capability, outcome class, `duration_ms`, never payload text, never a window title — plus the companion log line; the service writes its usual per-command rows.

Configuration (all `PAGENTOS_AGENT_`-prefixed): service `OperatorEnabled` (default false); companion `OperatorEnabled` (default false), `TerminalAllowlist` (`;`-separated patterns; empty = the default list), `OperatorRoots` (`;`-separated directories; empty = the owner's document folders and the fixture root, see `file.open`). Error classes added for the family, in the schema and the broker's mirror: `focus_mismatch` (retryable), `permission_denied` (never), `postcondition_failed` (retryable).

## 6j. Capability family: documents — File & Document Intelligence (M20)

The documents family rides this protocol unchanged — one command envelope, one lifecycle, one idempotency store, one audit log. The binding specification is **`docs/M20_FILE_DOCUMENT_INTELLIGENCE_SPEC.md`** §2 (ADR-0083); this section carries the same contract and states what the companion guarantees on the device side. The owner's rule: the system understands the owner's local documents with exact provenance — every answer names the file by identity and the place inside it.

**Names** (`AgentCapabilities.Documents`, 6 — 7 since M22, no family marker — every name is an operation): `file.search`, `file.locate`, `file.inspect`, `file.read`, `file.compare`, `document.extract`, and since M22 `file.fetch` (§6k, appended last). There is no delete, move or write name (ADR-0083 decision 7); `file.fetch` is the family's one creator — a NEW file in the Downloads root, never over an existing one (ADR-0085 decision 4).

- **Advertisement and routing.** The family appears in `hello.capabilities` and the enrollment manifest **only when `OperatorEnabled=true`** on the service AND on the companion — the same gate as §6i, because it is the same trust decision (the companion may touch the owner's files); the deployed 0.1.0 / 0.2.0 agent advertises neither family; the first agent that does is 0.3.0. Order in the manifest: desktop, alarm, ambient, display, browser, operator, documents — an append, never a reshuffle. Every name is interactive (`AgentCapabilities.IsInteractive`, `IsDocuments`): the Device Service (Session 0) forwards it over the authenticated companion pipe and never opens a file itself. With `OperatorEnabled=false` the service answers `capability_missing` (not retryable) before the pipe; a companion without the documents object answers the same; no companion connected is `dependency_unavailable` (retryable). The service caps one command at **30 s**; the companion budgets what is left less the usual headroom and answers `timeout` (retryable) when it elapses, `cancelled` on cancel. Requests run on the companion's concurrent (long-running) path, like the operator's.

**Identity.** `file_id = "file:" + first 32 hex of SHA-256( lower(volume serial as 8 hex) + "|" + casefold(full resolved path) )` — the volume serial from `GetVolumeInformationW` on the path's root, the casefold the invariant culture's lower-casing (never the Turkish culture's `I→ı`), the path the RESOLVED one (§6i's resolve-then-contain); a file keeps its id across edits, two same-named files in two folders never share one, two spellings of one file fold to one. `doc_id = "doc:" + SHA-256(bytes)` — a byte-identical copy at another path has the same doc id, an edit changes it. A file record is always `{file_id, path, name, extension, size, mtime (ISO-8601 UTC, "Z"), sha256?}`; `path` is the resolved path inside the roots; `sha256` is present when size ≤ 8 MiB AND the record came from a single-file capability — a search never opens a file, so its records carry no content hash (`file.locate` on the hit does). Kinds: `docx | xlsx | pptx | pdf | md | csv | json | source | txt | unknown` (`source` = .py .ps1 .cs .ts .tsx .js .sh .sql .yaml .yml .toml .ini .xml .html .css; `.tsv` is `csv`, `.markdown` is `md`, `.log` / `.text` are `txt`).

**`file_id` resolution.** A `file_id` is resolved from the companion's per-process memo of the ids it issued (search, locate, inspect, read, extract and compare fill it); an id the companion never issued, or one whose file is gone, is `not_found` — the planner searches again. A `path` argument is accepted everywhere a `file_id` is.

**Confinement.** Every path argument — search roots included — must RESOLVE inside `AuthorisedRoots` (§6i: `OperatorRoots`, default the owner's Documents / Desktop / Downloads / Pictures / Videos / Music and the operator fixture root; every junction, mount point and symbolic link followed before the comparison), else error class `permission_denied` — and the argument is never echoed back, so an answer never reveals whether an outside path exists. A path whose PARENT resolves inside the roots but which is not there is `not_found`. Reparse points are never followed by a search — not as a directory to descend into, not as a file to list — so a link planted inside a root cannot make the search read outside it. Names that carry secrets are never opened, hashed or listed: `.env*`, `*.pem`, `*.key`, `*.pfx`, `*.p12`, `id_rsa*`, `id_ed25519*`, `*.kdbx`, `secrets.json` → `permission_denied` (the message carries the detail `secret_bearing_name`). The checks run in this order, before any I/O on the file: payload validation, roots, secret name, size from the directory entry.

**Bounds.** Search ≤ 200 results, ≤ 20 000 directory entries walked, 10 s (every one reported as `truncated: true` with `stop_reason` = `max_results | max_entries | timeout`); read ≤ 65 536 chars per call (`offset`/`length` window the text; `total_chars` counts the characters decoded — the whole file up to the 4 MiB prefix below — and `truncated: true` says the window or the prefix cut); extract ≤ 65 536 chars of block text (`max_chars` lowers it; the block that crosses the budget is cut and flagged `truncated: true`, the rest dropped, the result says `truncated: true` — never a silent cut); files ≤ 50 MiB for reading and extraction, checked from the directory entry before the file is opened and again on the open handle (`unsupported_format`, detail `too_large`); PDF ≤ 200 pages — a longer document is refused (`unsupported_format`, detail `page_bound`) before any page is read unless the request names a `page_range` of at most 200 pages, which is read as asked (`file.inspect` still reports the true count); XLSX ≤ 2 000 rows per sheet (beyond: `truncated: true`, the counts still true).

**Decompression and read bounds (ADR-0083 addendum 3; `DocumentBounds` in the companion).** What a file would make the companion DO is bounded before the parser is entered, so a hostile file is a typed refusal with the numbers named, never an out-of-memory in the process that also hosts the operator. An OOXML package (docx / xlsx / pptx) is refused — `unsupported_format`, detail `decompression_bound`, the SDK never opened — when its parts' uncompressed lengths, read from the zip's central directory without inflating a byte, sum past 64 MiB, when it has more than 10 000 parts, or when a part above 1 MiB inflates more than 100:1; a file that is not a zip is left to the SDK's own verdict (`parse_failed`). Every stream a PDF inflates (at open, per page, per font) goes through a bounded filter provider and is refused (`decompression_bound`) past 32 MiB per stream or 256 MiB per document; one page's text is kept up to 256 KiB (the block says `truncated: true`). A text-like file is read as a 4 MiB prefix through one handle — `file.read`, `file.inspect` (which then carries `truncated: true`, its `lines` being the prefix's), `file.compare` and the CSV / MD / source / TXT extractors (`truncated: true`; the structure counts what the prefix held; a cut inside a multi-byte character is moved back to the last whole one) — and a JSON document is read whole up to 8 MiB and refused beyond (`too_large`). A secret-bearing NAME is refused lexically before anything is looked up, so it answers `permission_denied` / `secret_bearing_name` whether or not the file exists.

| capability | payload | result |
|---|---|---|
| `file.search` | `{roots?: [path], pattern: string (glob "*.pdf" or a name fragment "sözleşme"; casefold + diacritics-insensitive), extensions?: [".pdf"], max?: ≤200, modified_after?: ISO}` | `{files: [record], truncated, searched_roots: [path], entries_walked, stop_reason?}` |

**References (the strings an answer cites; `truth.json.reference_scheme` is normative).** DOCX: `p<n>` per non-empty paragraph in order (`kind = heading|paragraph`, `level` from the `Heading N` style), `t<n>` per table (`rows`, tab/newline text); `structure.headings/tables/paragraphs`. XLSX: `sheet:<name>!A<r>:<lastcol><r>` per non-empty row (tab-joined cell texts, gaps empty; a formula cell's text is `"=" + formula`, the block carries `formulas: {"B6": "B5*0.2"}` and `sheet`), `structure.sheets[{name, rows, columns}]`, `structure.formulas[{ref: "sheet:<name>!B6", formula}]`. PPTX: `s<n>` per slide (`title` = the title placeholder; text = title then body paragraphs), `structure.slides[{index, title}]`, `structure.slide_count`. PDF: `p<n>` per page (content order, whitespace-normalised), `structure.pages`. MD: `h<level>:<title>` per heading section (text = the section body; a repeated heading is `h2:Title#2`; text before the first heading is `p<n>` paragraphs), `structure.headings`. CSV: `r<n>` per line including the header, `structure.columns/rows/delimiter`. JSON: `$.<key>` per top-level key (compact JSON of the value, numbers as written, non-ASCII unescaped; a top-level array is `$[i]`), `structure.keys`. Source: `L<a>-<b>` per 40-line chunk, `structure.symbols[{name, line}]` from `def|class|function|public …(` lines, `structure.lines/language`. TXT: `p<n>` per blank-line paragraph. `title`: the package/PDF information title, else the first heading / slide title, else the file name without extension (DOCX/XLSX/PPTX/PDF); the first `#` heading (MD); null otherwise.

**Error classes.** `validation_error` (the spec's `invalid_argument`: a missing or malformed field, a relative path, a directory where a file was named), `not_found`, `permission_denied`, `unsupported_format` (new in M20, with `not_found`: `frames.py` `ERROR_CLASSES`, the device-protocol schema, the C# taxonomy; never retryable; the message names the reason and carries the detail `too_large | not_text | unknown_kind | parse_failed | decompression_bound | page_bound`), `timeout`. A format the device cannot parse answers `unsupported_format` with the reason, never an empty success. Every result passes the browser family's forbidden-key scan (§6i) before it leaves the companion.

**Extraction runs on the device**, in C#, behind per-format provider interfaces (`IDocumentExtractor`): `DocumentFormat.OpenXml` 3.5.1 (MIT) for DOCX/XLSX/PPTX — parts are read through the SDK's package model; the zip's central directory is read once by hand, without inflating an entry, to bound decompression before the SDK is entered — `PdfPig` 0.1.16 (Apache-2.0) for PDF, with the companion's bounded filter provider installed through `ParsingOptions.FilterProvider`, native code for the text-like kinds (encoding by BOM, strict UTF-8, a UTF-16 heuristic, Latin-1 as the fallback; a NUL or more than 1 % control characters means "not text"). Both packages are recorded in `docs/THIRD_PARTY_COMPONENTS.md`.

**Audit and log.** One `document_request` row per request — capability, outcome class, `duration_ms`, never a path, never a file name, never text — plus the companion log line; the service writes its usual per-command rows.

## 6k. Capability: `file.fetch` — a Cloud Core render onto the owner's machine (M22)

The device half of the Artifact Factory (`docs/M22_ARTIFACT_FACTORY_SPEC.md` §4, ADR-0085 decision 4): "Bunu aç" after "Bana bir bütçe tablosu yap" fetches the validated render and opens it. A member of the documents family — the same `OperatorEnabled` gate on both halves, the same 30 s cap and remaining-budget rule, the same concurrent path, the same `document_request` audit row (capability, outcome, `duration_ms`; never the URL, never the name), the same forbidden-key scan — appended as its seventh name; the first agent that advertises it is **0.4.0**. It is the family's ONE creator: it brings a render Cloud Core made into the owner's Downloads root as a NEW file. It never replaces, moves or deletes anything, and a refusal at any step leaves nothing behind. At most **two** fetches are in flight per companion (ADR-0085 addendum 3): a third is refused before any request with `dependency_unavailable` (retryable, detail `fetch_busy`).

Payload: `{"url":"<https://core/v1/artifacts/renders/fetch/{token}>","name":"bütçe.xlsx","sha256":"<64 hex>","size":<int 1…52428800>,"open":<bool>?,"application":"notepad"?}`. The URL is never the owner-session-gated `GET /v1/artifacts/{id}/renders/{fmt}` a browser uses (ADR-0085 addendum 5): `{token}` is a single-use, ten-minute, 256-bit value minted for exactly this render (artifact id + format + content hash) that the device redeems with no owner token, cookie or header of its own — the path still starts with `/v1/artifacts/` (step 4 below).
Result: `{"file":<record §6j>,"path":"<resolved>","verified":true,"sha256":"<64 hex>","bytes":<int>,"mark_of_the_web":<bool>,"opened":<file.open result>?}`

The checks, in the order they run — everything before step 5 costs no request:

1. **Shape** (`validation_error`, naming the field): `url` an absolute http(s) URL ≤ 2048 chars with no credentials; `name` (below); `sha256` 64 hex; `size` a whole number 1 … **50 MiB**; `open` a boolean; `application` only with `open: true`.
2. **`name` is a plain file name**, sanitised by trimming and otherwise REFUSED rather than rewritten (`validation_error`): ≤ 120 characters; none of the file system's invalid characters (both separators, the drive colon, wildcards, the C0 control characters); no C1 control character and no Unicode format character (category Cf: the bidirectional overrides and isolates U+202A–E / U+2066–9, the marks U+200E/F, zero-width characters, the BOM, tags — invisible, or reordering what Explorer shows); well-formed UTF-16; no `..` anywhere, not `.`; no trailing dot or space; not a reserved device name (`CON`, `NUL`, `COM1`…, with or without an extension); not a secret-bearing name (§6j's list); not an executable extension (§6i's `file.open` list, shared: `.exe .bat .cmd .com .scr .ps1 .psm1 .vbs .vbe .js .jse .wsf .wsh .msi .msp .lnk .hta .reg .cpl .inf .pif .url .jar` and the macro-enabled Office family `.docm .dotm .xlsm .xlsb .xltm .xlam .pptm .potm .ppam .sldm` — a document that carries code is a program here, on both names); not the companion's own temp prefix. The unique suffix on collision (`bütçe (2).xlsx`) is the companion's, outside the 120.
3. **`open` needs the operator** — a companion built without `file.open` answers `capability_missing` before any request.
4. **Origin** (`permission_denied`, never retryable): the URL's scheme, host and port must equal **the origin the device dialled** for its Cloud Core connection (ADR-0069's rule for `desktop.play_audio`): the broker REST base reduced to scheme + host + port. The **Device Service** refuses before the pipe, against its own configuration; it also tells the companion that origin in every pipe challenge (`service_challenge.broker_origin`, an optional, additive field of the internal IPC), and **the companion refuses again** against what it was told. A companion that was never told (an older service, no broker URL) refuses every fetch — it never guesses an origin from its own configuration. The path must start with `/v1/artifacts/`. The message names `payload.url` and says "beklenen köken değil"; it never repeats the URL's host.
5. **The Downloads root** (companion `DownloadsRoot`, default the owner's Downloads known folder) must itself RESOLVE inside `OperatorRoots` (§6i's resolve-then-contain) at fetch time, else `permission_denied` — and the only thing ever written is a new file directly inside it.
6. **The request** is `GET` of exactly the URL the payload carried — the Cloud Core signs the URL, and the companion adds **no owner token, no cookie, no header of its own**. **Redirects are never followed** (`AllowAutoRedirect=false`): any 3xx is `dependency_unavailable` (not retryable), a redirect onto the same origin included — the URL Cloud Core signed is the URL. Any other non-2xx is `dependency_unavailable` (retryable for 5xx). No client-side decompression: the bytes counted and hashed are the bytes on the wire. No proxy: the request goes to the origin directly, whatever the system or environment proxy settings say (`UseProxy=false`).
7. **Size, while streaming.** A `Content-Length` that differs from `size` is refused on the headers, unread (`validation_error`). The body is counted as it streams into a temp file (`.pagentos-fetch-<id>.part`, `CreateNew` beside the final name, so a planted reparse point is never opened; its handle is exclusive for reading and writing — only deletion is shared, which is what the rename needs — from the first byte until after the rename): one byte past `size` aborts the connection under the server, deletes the partial file and answers `validation_error` — a chunked body that keeps sending cannot make the companion keep writing. A body that ends short is `postcondition_failed`. Every read of the body is asynchronous and carries the cap token, so a peer that sends its headers and then goes quiet is abandoned at the cap, not waited for (below).
8. **Hash, before the rename.** The SHA-256 is computed while streaming and compared with `sha256` BEFORE the temp file gets its final name; a mismatch deletes it and answers `postcondition_failed` (message detail `sha256_mismatch`, never retryable). The rename happens while the streaming handle is still open, so nothing else can have written a byte between the hash and the name.
9. **The final name** is `name`, else `stem (2).ext`, `stem (3).ext`… — moved with `overwrite: false`, so an existing entry of any kind (a file, a directory, a reparse point squatting the name) is never replaced or opened, only skipped. **Then the file is checked again under its final name** (ADR-0085 addendum 3): re-opened exclusively (if something else holds it after a second of retries, it is deleted and the answer is `postcondition_failed` / `unverifiable_after_move`), its length and SHA-256 compared with `size` and `sha256` once more; a file that no longer matches — swapped under the name by whatever runs as the owner in the instant between the rename and the re-check — is deleted and the answer is `postcondition_failed` / `sha256_mismatch_after_move`. Nothing with the requested name is ever REPORTED unless it has the requested hash at the moment it is reported. The kept file gets the NTFS **Mark-of-the-Web** (`Zone.Identifier` stream, `[ZoneTransfer]` / `ZoneId=3`, no URL), so Office opens it in Protected View and the shell asks before running anything from it, as it does for a browser download; `mark_of_the_web: false` in the result means the volume could not carry the stream (FAT/exFAT) — the file was kept without it. What is reported is the path the file system resolved for the kept file, checked to lie inside the Downloads root once more; the record is §6j's (`sha256` present under 8 MiB), the `file_id` is issued and resolves again.
10. **`open: true`** runs the operator's real `file.open` on the resolved path — its confinement, its `application` argument policy (`notepad` and `explorer` take the path; a browser, `calc` or `powershell` is refused), its window wait — on the rest of this request's budget, and `opened` carries its observation (`{opened: true, path, pid, window_id, observed: {window, window_appeared}}`). A fetch that succeeded but could not open reports the refusal INSIDE `opened` (`{opened: false, error: {class, message, retryable}}`) and keeps the file: the fetch did happen.

The family's 30 s cap is enforced inside the download on every read — headers, each body chunk, the file writes all carry the cap token (linked to the command's budget), and the fetch is awaited end to end rather than run on a pool thread — so an origin that stalls at any point answers `timeout` (retryable) within the cap, the connection is dropped and the partial file removed; measured on this machine, a peer that sent `200`, `Content-Length: 1000000` and ten bytes then nothing was answered `timeout` 30.003 s after the request and saw its connection closed at 30.002 s. A cancelled command removes the partial file and answers `cancelled`. Two downloads may be in flight per companion; a third is `dependency_unavailable` / `fetch_busy` (retryable) before any request, so two stalled peers cannot hold more than two slots and no thread at all. Configuration: companion `PAGENTOS_AGENT_DownloadsRoot` (empty = the Downloads known folder); the origin is never configured on the companion — it arrives with the challenge.

The lab (`tests/PagentOS.Agent.Tests/Documents/FileFetchTests.cs`) stands a local `HttpListener` on 127.0.0.1 in for the origin, pins the real dispatcher to it the way the challenge does, and proves every refusal above with the listener's request log and an empty Downloads root afterwards — including the chunked stream aborted between 50 MiB and the 80 MiB the server had, the redirect target that saw no request, the challenge carrying the origin over a real pipe, and Notepad opening a fetched `.txt` on a host with a desktop. Since ADR-0085 addendum 3 a raw `TcpListener` with no HTTP stack also stands in for the stalled peer (headers, ten bytes, silence): with the lab's 3 s cap the fetch answers `timeout` in 3.0 s, the peer sees the close, nothing is kept and the next fetch from the same origin works; a third fetch beside two stalled ones is refused as busy and the slots come back when they time out. The lab also flips a byte and replaces the file under its final name through the `BeforeFinalVerify` seam and sees both refused and removed, proves the `.part` cannot be opened for reading or writing by anyone else while it streams, reads `ZoneId=3` back from the kept file's `Zone.Identifier` stream, and checks each new extension is refused before any request on `file.fetch` and `permission_denied` on `file.open`.

## 6l. Capability family: projects — the App Factory's device half (M23)

The projects family rides this protocol unchanged — one command envelope, one lifecycle, one idempotency store, one audit log. The binding specification is **`docs/M23_APP_FACTORY_SPEC.md`** §3 (ADR-0086); this section carries the same contract and states what the companion guarantees. The owner's rule: an app the assistant made exists when it has been scaffolded into a real project on the owner's machine, run there in a bounded process, and its own tests have passed — and nothing of that touches the owner's other projects or processes.

**Names** (`AgentCapabilities.Projects`, 5, no family marker — every name is an operation): `project.scaffold`, `project.run`, `project.status`, `project.stop`, `project.test`. There is no delete name (ADR-0086 decision 5). The first agent that advertises the family is **0.5.0**.

- **Advertisement and routing.** The family appears in `hello.capabilities` and the enrollment manifest **only when `OperatorEnabled=true`** on the service AND on the companion — the same gate as §6i and §6j, because writing source and starting a process on the owner's machine is the same trust decision as touching the owner's files. Order in the manifest: desktop, alarm, ambient, display, browser, operator, documents, projects — an append, never a reshuffle. Every name is interactive (`AgentCapabilities.IsInteractive`, `IsProjects`): the Device Service (Session 0) forwards it over the authenticated companion pipe and never writes a file or starts a process itself. With `OperatorEnabled=false` the service answers `capability_missing` (not retryable) before the pipe; a companion without the projects object answers the same; no companion connected is `dependency_unavailable` (retryable). The service caps `project.scaffold`, `project.run`, `project.status` and `project.stop` at **30 s** and `project.test` at **5 min 30 s** (its own bound is 5 min); the companion budgets what is left less the usual headroom and answers `timeout` (retryable) when it elapses, `cancelled` on cancel. Requests run on the companion's concurrent (long-running) path, so the heartbeat's status request is never behind a test run.

**The Projects root.** Source is written into exactly ONE directory: companion `ProjectsRoot`, default `%USERPROFILE%\Documents\PagentOS Projects`, which `OperatorOptions` always lists among the authorised roots (appended to an owner-configured `OperatorRoots` too), so `file.open` / `file.reveal` reach what was written. It is created on the first scaffold, but only under a parent that RESOLVES inside the authorised roots (§6i's resolve-then-contain), and it must itself resolve inside them on every scaffold. A project lives at `<root>\<slug>`; a **slug** is a plain name (`[a-z0-9][a-z0-9-]{0,63}`, never a reserved device name), a **`project_id`** is `[A-Za-z0-9][A-Za-z0-9._:-]{0,127}`. The **marker** `.pagentos-project.json` (`{project_id, slug, scaffolded_at, manifest}`) is written LAST by the scaffold and is what makes a folder the assistant's: a folder under the root that exists, is not empty and has no marker is the owner's and is `permission_denied` (detail `owner_folder`), one whose marker names another `project_id` is `permission_denied` (`other_project`), a folder that is a link is refused, an empty folder is used. A `project_id` is resolved from the companion's memo, else by reading the markers of the folders DIRECTLY under the root (links never followed, at most 2 000 entries); an id nobody scaffolded is `not_found`. The marker's manifest — validated once at scaffold time, written by the companion — is what `project.run` / `project.test` re-parse; a marker edited into a non-allowlisted command is `permission_denied` before any process exists, whoever edited it.

**The manifest and the runtime allowlist** (ADR-0086 decisions 1 and 3). `manifest: {entry, port, run: {key: command}, test?: {key: command}}` — `entry` a relative file of the file list, `port` in 1024…65535, keys `[a-z][a-z0-9_-]{0,31}`, at most 8 commands per section. Every command must match one of a FIXED list, token for token, and is stored as an argument LIST — the companion never hands a command line to a shell: `python -m http.server <port> --bind 127.0.0.1` (run; `<port>` or the number, which must equal `port`); `node <entry>` (run; exactly the manifest's entry); `node <relative file of the project>` (test); `npm --prefix <root> run start` / `run test` — only when the template shipped `package-lock.json` in the file list (`<root>` is replaced by the project folder at run time; npm runs through `node.exe` and the `npm-cli.js` beside it, never `npm.cmd`). Anything else — another program, an absolute path, `..`, a composition or quote character, a second argument — is `permission_denied` (detail `command_not_allowlisted`) at scaffold and again at run. The payloads of `project.run` and `project.test` name a **`command_key`** into these maps (default: the section's first key); a command line never crosses the pipe. `python.exe` / `node.exe` are resolved from the companion's PATH, skipping the Store's `WindowsApps` aliases; a machine without one answers `dependency_unavailable` (`runtime_missing`, not retryable).

**The run** (ADR-0086 decision 3). The process is the companion's OWN child, created by it and placed in a **Windows Job Object** the instant it exists (and checked to be there): `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` (a companion that dies takes its children with it), committed memory ≤ **512 MiB**, user-mode CPU time ≤ **10 min**, at most **8** processes in the job, `DIE_ON_UNHANDLED_EXCEPTION`, every UI restriction (`JOB_OBJECT_UILIMIT_ALL`: no clipboard, no desktop switch, no `ExitWindows`, no USER handles outside the job), and **no breakaway**. Its environment is a scrubbed copy of the companion's: every `PAGENTOS_*` variable and every credential-shaped name (`*_TOKEN`, `*_SECRET`, `*_PASSWORD`, `*_PASSWD`, `*_KEY`, `*_CREDENTIAL(S)`, `*_AUTH`, and the bare `TOKEN`, `SECRET`, `PASSWORD`, `APIKEY`, `API_KEY`, `AUTHORIZATION`) removed, the system directories first on PATH, `NO_COLOR=1`, Python unbuffered and UTF-8. Its working directory is the project folder; stdout and stderr go to `<root>\<slug>\.pagentos\run.log`, cut at **1 MiB** (a marker line, then nothing more; the last 8 KiB are kept in memory as `log_tail`). The manifest's port is checked bindable on `127.0.0.1` first (`dependency_unavailable` / `port_busy`, retryable, after a 2 s grace for a port a just-stopped run is still releasing). At most **2** projects run at once (`dependency_unavailable` / `projects_busy`, retryable); a project already running is `already_running`. A run ends by itself after **30 min**. `project.run` answers once the port ANSWERS a TCP connect (probed every 100 ms for at most 20 s within the budget): a process that exits first is `postcondition_failed` (`exited_early`, not retryable, the message and detail carrying `exit_code` and the log tail; status then says `exited`); one that never answers is ended and `postcondition_failed` (`port_never_answered`, retryable). The exit of the entry process ends the whole job. `project.stop` terminates the run's job — only its members, never a process by pid, so nothing of the owner's (Chrome, PowerShell, Node, Python) is ever touched — and waits ≤ 5 s for the process to be gone (`postcondition_failed`, retryable, if it is not); stopping what is not running answers `stopped: true, was_running: false`. Runs never outlive the companion (kill-on-close), so after a restart every project reads as `scaffolded`.

| capability | payload | result |
|---|---|---|
| `project.scaffold` | `{project_id, slug, files: [{path, text}], manifest}` — ≤ 200 files, ≤ 2 MiB of UTF-8, text only (no NUL or control character but tab/newline/return, well-formed UTF-16); every `path` relative with `/` or `\`, ≤ 200 chars, ≤ 8 segments, no `.`/`..`/empty segment, no drive, leading separator or UNC form, no invalid or format character, no trailing dot or space, no reserved device name, no launcher extension (everything `file.open` refuses except `.js`), never the marker, never under `.pagentos/`, no two paths equal case-insensitively, and none whose normalised form the family's forbidden-key scan would refuse as a result key (`sha256_by_path` is keyed by path) — all `validation_error` naming the field, before a byte is written | `{project_id, slug, root_path, files_written, sha256_by_path: {path: hex}, manifest}`; every directory a file lands in is RESOLVED and must lie inside the project folder (a link planted inside a project resolves outside and is `permission_denied` with the scaffold stopped); a re-scaffold of the same `project_id` overwrites its own files and deletes nothing |
| `project.run` | `{project_id, command_key?}` | `{project_id, slug, pid, port, url: "http://127.0.0.1:<port>/", started_at, command_key, log_path}` |
| `project.status` | `{project_id}` | `{project_id, slug, root_path, state: scaffolded\|starting\|running\|exited\|stopped, pid, port, uptime_s, log_tail, started_at?, command_key?, exit_code?, stop_reason?: stop\|lifetime\|port_never_answered\|cancelled\|start_failed\|shutdown, log_truncated?}` |
| `project.stop` | `{project_id}` | `{project_id, slug, stopped: true, was_running, pid?}` |
| `project.test` | `{project_id, command_key?}` | `{project_id, slug, command_key, exit_code, passed, failed, counts_parsed, report_tail, truncated, duration_ms, log_path}` — the manifest's test command in a job with the same bounds, ≤ **5 min** (then `timeout`, retryable, the job ended); at most 2 test runs at once (`tests_busy`); output to `.pagentos\test.log` under the same 1 MiB bound; `passed` / `failed` parsed from the runner's last `passed: N` / `failed: M` lines (also `N passed|passing`, `M failed|failing|failures`), null with `counts_parsed: false` when it printed none |

**Error classes.** Nothing new: `validation_error`, `permission_denied` (never retryable; details `owner_folder`, `other_project`, `command_not_allowlisted`), `not_found`, `dependency_unavailable` (details `port_busy`, `projects_busy`, `already_running`, `tests_busy`, `runtime_missing`), `postcondition_failed` (`exited_early`, `port_never_answered`), `timeout`, `cancelled`. Every result passes the browser family's forbidden-key scan (§6i) before it leaves the companion.

**Terminal.** The `terminal.execute` allowlist (§6i) gains ONE project-scoped entry, `node <project-entry> --help`: the token matches one absolute path that resolves under the Projects root, inside a folder that carries the marker, and IS that folder's manifest `entry` — an app the assistant made, its help text, read-only; another file of the project, a script beside the root, a folder without the marker, a link, or any other argument does not match.

**Audit and log.** One `project_request` row per request — capability, outcome class, `duration_ms`, never a path, never file text, never a log line — plus the companion log line; the service writes its usual per-command rows.

Configuration (all `PAGENTOS_AGENT_`-prefixed): companion `ProjectsRoot` (empty = `Documents\PagentOS Projects`); the family's gate is `OperatorEnabled` on both halves.

The lab (`tests/PagentOS.Agent.Tests/Projects/`) works under `%TEMP%\pagentos-operator-fixture\projects\<run-id>\Projects` with the real dispatcher and real runtimes (a test that needs `python` or `node` skips with the reason when the machine lacks it): the scaffold's files, marker and hashes; every refused path, slug, size and manifest with nothing written and a counting seam proving no process started; an owner's folder untouched; a junction inside a project and one squatting a project's name; a real `python -m http.server` child answering `GET /` from inside a job whose limits are read back from the kernel; two runs and a third refused; the stop that ends the job while a python the test started outside it survives, and the runner's dispose doing the same; the early exit, the port that never answers, the lifetime, the busy port; the environment scrub read from inside a node child; the template's runner passing and failing with its counts; the test bound, the caller's cancel, the memory bound ending a child that allocates 768 MiB, the 1 MiB log; the terminal token; the advertisement, the caps, and the whole service → pipe → companion chain scaffolding a project and carrying typed refusals.

## 6m. The two 3D runtimes and `scene.inspect` — the App Factory's 3D half (M25)

M25 adds no new machinery to this protocol: the two 3D editors ride the **projects** family's manifest allowlist and its Job Object runner, and one new name, `scene.inspect`, reads back what a driver wrote. The binding specification is **`docs/M25_CREATIVE_3D_SPEC.md`** §3/§6/§7 (ADR-0088 decision 3). The owner's rule: the assistant creates and changes 3D scenes through the tools' own scripting interfaces, proves every change by reading the scene back from the tool and rendering it, and never claims control of an application it cannot actually drive.

**Name** (`AgentCapabilities.Scenes`, 1, no family marker): `scene.inspect`. There is no `scene.create`, no `scene.render` and no free-form runner on the device — a scene is created by `project.run` of an allowlisted 3D runtime, and this name only reads back. The first agent that advertises it is **0.6.0**.

- **Advertisement and routing.** Appended after the projects family — desktop, alarm, ambient, display, browser, operator, documents, projects, **scenes** — and advertised only when `OperatorEnabled=true` on the service AND on the companion, because writing a scene into the owner's Documents and starting an editor there is the same trust decision as §6i, §6j and §6l. Interactive (`AgentCapabilities.IsInteractive`, `IsScenes`), executed by the same companion object as the projects family, on the same long-running path. `capability_missing` (not retryable) from the service before the pipe when the flag is off, and from a companion built without the projects object. The service caps `scene.inspect` at **30 s**; M25 raises the cap on **`project.run`** alone to **10 min 30 s** (Unity's bound plus headroom) because a 3D run is a batch run the companion waits out — a web run still answers within its 20 s port wait, since the cap is a ceiling and not a wait.

**The 3D root.** The two editors run under exactly ONE directory: companion `ProjectsRoot3d`, default `<ProjectsRoot>\3d` (so `%USERPROFILE%\Documents\PagentOS Projects\3d`). `OperatorOptions` always lists it among the authorised roots, appended to an owner-configured `OperatorRoots` and beside the Projects root, and it is resolved-then-contained on every use (§6i). It is created on the first 3D scaffold, together with any missing directory above it, but only under an ancestor that resolves inside the authorised roots. **The owner's own project folders are never under it**: an M23 project lives at `<ProjectsRoot>\<slug>`, the owner's own work lives wherever the owner put it, and a `project.scaffold` that asks for the slug `3d` is `validation_error` by name — that folder IS the 3D root. Everything else about a 3D project is M23's, unchanged: the `<3d root>\<slug>` layout, the slug and `project_id` alphabets, the `.pagentos-project.json` marker written last, the owner-folder and other-project refusals, the id resolved from the markers directly under the root. `project.scaffold` chooses between the two roots with a payload field `root: "projects" | "3d"` — a CLOSED vocabulary of two words, never a path (anything else is `validation_error`); the default is `projects`, so M23 payloads are unchanged, and the result echoes `root`. A 3D manifest may omit `port` (a batch run binds nothing; the marker records `port: 0` and the re-parse accepts it back).

**The two argv shapes** (ADR-0088 decision 3). The M23 discipline is unchanged: the match is against a FIXED list, **token for token**, never a string prefix; the command is stored as an argument LIST and no command line ever reaches a shell; the verdict is reached at scaffold time and again at run time from the marker, before any process exists. Under the 3D root — and only there; both are `permission_denied` in a project of the Projects root — two more forms are admitted:

| runtime | the only form | resolved to |
|---|---|---|
| Blender | `blender --factory-startup -b [<scene.blend>] --python <driver.py> -- <plan.json> <out.json>` | the installed `blender.exe` |
| Unity | `unity -batchmode -nographics -quit -projectPath <root> -executeMethod PagentOS.SceneDriver.Run -planPath <plan.json> -outPath <out.json> -logFile <log>` | the Hub's `Unity.exe` |

`--factory-startup` is the first flag of every Blender command and is never optional: opening a saved `.blend` without it loads the OWNER'S installed Blender add-ons into the run — third-party code inside the bounded job — and on the owner's machine one of them starts a watchdog thread that never stops, so the editor never exits and the run burns its whole bound (both measured 2026-09-08 by running the Cloud Core's own command against the real editor). The **scene file after `-b` is optional**, and only there: a project's first run has none to open, because a `.blend` that does not exist cannot be opened at all and `project.scaffold` writes text only, so no binary starter scene can be placed. The driver saves `scene.blend`; every later run names it. Eight tokens without the scene, nine with it, and nothing else admitted in either position.

Every path token must be RELATIVE and inside the project (the scaffold's normalisation: no `..`, no drive, no leading separator, no UNC form) and must carry the extension its position requires (`.blend`, `.py`, `.json`, `.json`; `.log` for Unity's log) — the child's working directory is the project folder, so nothing has to be absolute for the editor to find it, and nothing absolute is ever accepted, which is what keeps the owner's own `.blend` and the owner's own Unity project out of reach before a process exists. `<root>` is M23's placeholder, replaced by the project folder at run time; it is the only `-projectPath` Unity may be given. `-executeMethod` may name **only** `PagentOS.SceneDriver.Run`, the shipped driver's entry point. An extra token, a missing one, `-P` for `--python`, a missing `--`, a missing `-nographics` or `-quit`, another program, or any composition or quote character is `permission_denied` (detail `command_not_allowlisted`).

**The editors are DETECTED, never searched for on PATH.** `blender` resolves to the `InstallLocation` of a product named Blender in the uninstall registry (both hives), else the highest version directory under `<Program Files>\Blender Foundation\<…>\blender.exe`; `unity` resolves to the highest `<Program Files>\Unity\Hub\Editor\<version>\Editor\Unity.exe`. A PATH search would let anything named `blender.exe` earlier on PATH be what "blender" means. Nothing is executed to learn a version (the registry's `DisplayVersion` and the Hub's directory name say it). A machine without the editor answers `dependency_unavailable` (detail `runtime_missing`, not retryable), naming where it looked.

**The run.** Everything about the containment is §6l's: the companion's OWN child, in a Job Object configured before the process exists and checked to hold it, `KILL_ON_JOB_CLOSE`, no breakaway, `DIE_ON_UNHANDLED_EXCEPTION`, every UI restriction (`JOB_OBJECT_UILIMIT_ALL`), the scrubbed environment (every `PAGENTOS_*` and credential-shaped variable removed), the working directory the project folder, stdout and stderr to `<root>\<slug>\.pagentos\run.log` cut at 1 MiB with the last 8 KiB kept, one of the 2 run slots, `already_running` / `projects_busy` as before, and `project.stop` ending only that job. What differs is the **bounds** and the **shape of the wait**:

| runtime | wall clock | job memory | processes in the job |
|---|---|---|---|
| Blender | **5 min** | **2 GiB** | 32 |
| Unity | **10 min** | **4 GiB** | 32 |

A batch run binds no port, so nothing is probed: **`project.run` waits for the exit** (bounded by the runtime's limit and by what is left of the command's budget) and answers `{project_id, slug, runtime, command_key, batch: true, exit_code, seconds, log_tail, log_truncated, log_path, pid}` — no `url`, no `port`. A run that outstays its bound has its job ended and answers `timeout` (retryable) with the tail; a cancelled command answers `cancelled`. Unity writes almost nothing to stdout and everything to its `-logFile`, so the tail a Unity run reports is its stream output plus the tail of that file, read against the project folder.

**Unity without a licence is `dependency_unavailable`, never `device_error`.** A Unity run that exits **198**, or whose log carries "No valid Unity Editor license found", is refused with detail `unity_licence`, `exit_code`, the licensing client's own line as `detail_line` (also inside the message), and the log tail — because the editor IS installed and DID start; what is missing is an entitlement only the owner can obtain (a Unity Hub sign-in, `docs/OWNER_ACTIONS.md` item 32). The Cloud Core can then say "Unity lisansı yok: yapılamadı" rather than claiming a scene was built. Measured on the owner's machine 2026-09-08 at 09:55Z and again at 13:24Z: exit 198 after ~2 s.

| capability | payload | result |
|---|---|---|
| `scene.inspect` | `{project_id}` | `{project_id, slug, root_path, inspection_path, inspection: <the driver's out.json>, render: {path, bytes, sha256, verified: true, png_base64} \| null}` |

The checks, in order: the payload's shape (`validation_error`); the project — looked up in the Projects root's markers, then the 3D root's; an id nobody scaffolded is `not_found`, and so is a project of the Projects root (it has no scene to inspect). Then `out.json` at the project root: absent is `postcondition_failed` / `inspection_missing` (nothing has run, or the run ended before the driver wrote its read-back — a different answer from "you may not look", which is what the Cloud Core needs to tell apart); larger than **256 KiB** is `postcondition_failed` / `inspection_bound` and it is not read; not JSON, or a top level that is not an object, is `postcondition_failed` / `inspection_not_json` — the whole point of the file is that it IS the tool's answer. Then the render the inspection declares under `render: {path, bytes|size, sha256}`: no `render` key at all is a valid answer (`render: null` — the plan only inspected); a declared render with no `path` or no 64-hex `sha256` is `render_undeclared`; a file that is not there is `render_missing`; one larger than **512 KiB** is `render_bound` and it is not read; and one whose bytes do not hash to the sha256 the DRIVER recorded is `render_sha256_mismatch` — a picture nobody can vouch for is not passed on as the tool's work. Every path inside `out.json` is normalised and resolved inside the project folder (junctions and links followed) before anything is opened; one that points elsewhere is `permission_denied` and nothing is read. The result passes the browser family's forbidden-key scan (§6i) like every other result — note that the inspection's own keys are the driver's, so a driver that wrote a key such as `token` would have the whole result refused.

**Error classes.** Nothing new: `validation_error`, `permission_denied` (`command_not_allowlisted`), `not_found`, `dependency_unavailable` (`runtime_missing`, `unity_licence`, `already_running`, `projects_busy`), `postcondition_failed` (`inspection_missing`, `inspection_bound`, `inspection_not_json`, `render_undeclared`, `render_missing`, `render_bound`, `render_sha256_mismatch`), `timeout`, `cancelled`.

**Audit and log.** The same one `project_request` row per request — capability, outcome class, `duration_ms`, never a path, never file text, never a log line.

Configuration (all `PAGENTOS_AGENT_`-prefixed): companion `ProjectsRoot3d` (empty = `<ProjectsRoot>\3d`); the gate is `OperatorEnabled` on both halves. The companion's startup log names the 3D root and which editors were detected, before anything is asked of them.

The lab (`tests/PagentOS.Agent.Tests/Scenes/`) works under `%TEMP%\pagentos-operator-fixture\scenes\<run-id>\Projects\3d` with the real dispatcher and the REAL editors (a test that needs one skips with the reason when the machine lacks it, so the runner — which has neither — still runs the allowlist, bounds and advertisement tests): both shapes admitted and stored as argument lists; 21 hostile variants refused before any process, with a counting seam in place of `Process.Start` proving the count stays 0 — a path outside the project, a `--python` pointing outside, an `-executeMethod` other than the driver, extra and missing tokens, `blender` without `-b`, a `.blend` that is not one, the owner's own Unity project as `-projectPath`, a shell composition; a marker edited into a hostile command refused at RUN time; the real `blender.exe -b` building a sphere, a camera and a sun on a fixture `.blend` and rendering a 160×120 Workbench still, `project.run` answering exit 0 and `scene.inspect` returning the read-back and the PNG with a matching sha256; the flipped byte, the escaped render path, the two bounds and the not-JSON refusals; the real `Unity.exe -batchmode -nographics` on a throwaway project, asserting whichever of the two states the machine is in (today: exit 198 with the licensing client's own line, and no claim that a scene was made); a slow Blender ended by its job at a 2 s lab seam with the job's limits read back from the kernel; and the advertisement, the caps and the whole service → pipe → companion chain.

## 6n. The four native build shapes and the `native` root — the Native Application Factory's device half (M28)

M28 adds **no capability name** to this protocol. That is the point, and it is M25's shape one root further: the .NET toolchain rides the **projects** family's manifest allowlist and its Job Object runner, under a third authorised root. A build is a batch `project.run`; a `dotnet test` is a `project.test`. The binding specification is **`docs/M28_NATIVE_APP_FACTORY_SPEC.md`** §5/§9 (ADR-0095 decision 4). The owner's rule: a distributable application exists when a real build produced a real artefact on this machine — and the build that produced it ran as a bounded child of the companion, under a root that is not where the owner keeps anything.

**Why no new name.** Every capability name is a thing a command aimed at this device can ask for, so a name is a surface. The four commands need no surface of their own: they are already reachable, already gated, and already contained by names the device advertises. Adding `native.build` would have moved the advertised manifest (85 capabilities with `-Operator` becomes 89), which means re-qualifying the arithmetic `scripts/qualify-staged-update.ps1` and `scripts/core/qualify-item28-unlocked.ps1` assert, for no capability the device did not already have. The manifest is unchanged: **40** with `-DisplayPower` and the browser worker, **85** with `-Operator`. (Cloud Core's `native.build` is a Living Core UI-state word — `app/uistate/contract.py`, v13 — and not a device capability; the two vocabularies do not meet.)

**The native root.** A compiler runs under exactly ONE directory: companion `ProjectsRootNative`, default `<ProjectsRoot>\native` (so `%USERPROFILE%\Documents\PagentOS Projects\native`). `OperatorOptions` always lists it among the authorised roots, appended to an owner-configured `OperatorRoots` and beside the Projects and 3D roots, so `file.*` and the documents family can read back the artefact a build produced. It is resolved-then-contained on every use (§6i): resolved FIRST — junctions, links, `..`, short names and all — and only then compared against the resolved root. It is created on the first native scaffold, together with any missing directory above it, but only under an ancestor that resolves inside the authorised roots. Cloud Core's mirror of this rule is `services/api/app/nativefactory/roots.py` (`NATIVE_SUBDIR`, `PROJECTS_FOLDER`), and the two are held together by a test that READS that file rather than restating the word (`NativeRootTests`): both suites can be green while the halves drift, and only a test that reads the other side catches a rename.

Everything else about a native project is M23's, unchanged: the `<native root>\<slug>` layout, the slug and `project_id` alphabets, the `.pagentos-project.json` marker written last, the owner-folder and other-project refusals, the id resolved from the markers directly under the root. `project.scaffold` chooses between the three roots with `root: "projects" | "3d" | "native"` — a CLOSED vocabulary of three words, never a path (anything else is `validation_error`); the default is `projects`, so M23 and M25 payloads are unchanged, and the result echoes `root`. A `project.scaffold` that asks for the slug `native` is `validation_error` by name — that folder IS the root. A native manifest may omit `port` (every one of its commands is a batch run and nothing binds one; the marker records `port: 0` and the re-parse accepts it back).

**The four argv shapes** (ADR-0095 decision 4). The M23 discipline is unchanged: the match is against a FIXED list, **token for token**, never a string prefix; the command is stored as an argument LIST and no command line ever reaches a shell; the payload names a **`command_key`** into the manifest; the verdict is reached at scaffold time and again at run time from the marker, before any process exists. Under the native root — and only there; all four are `permission_denied` in a project of the Projects root or the 3D root — these are admitted, and nothing else is:

| runtime | section | the only form | resolved to |
|---|---|---|---|
| dotnet | run | `dotnet build <project.csproj> -c Release` | the installed `dotnet.exe` |
| dotnet | test | `dotnet test <project.csproj> -c Release` | the installed `dotnet.exe` |
| dotnet | run | `dotnet publish <project.csproj> -c Release -r win-x64 --self-contained true -o <dir>` | the installed `dotnet.exe` |
| makeappx | run | `makeappx pack /d <dir> /p <package.msix> /o /nv` | the Windows Kits' `makeappx.exe` |

In exchange, the three web runtimes (`python`, `node`, `npm`) are **refused** under the native root: it compiles applications and does nothing else, and a native project that could quietly become a web server would be a second thing happening in the one root where a compiler is allowed to run.

`build` and `publish` and `pack` are run commands and `test` is a test command, and neither section admits the other's: a `project.test` whose key resolved to `dotnet build` would report a compile as a passing test suite, which is the difference between "it builds" and "its tests pass". `-c` may name only `Release` (a Debug build is not a distributable application) and `-r` only `win-x64`. **NOT `PublishSingleFile`**: measured 2026-09-09, single-file needs `Microsoft.NET.ILLink.Tasks`, which does not restore on this machine (NU1100); the self-contained FOLDER publish produces the same real EXE and is what the portable zip packages anyway. `/o` overwrites the package a previous run made; `/nv` skips semantic validation, which is what would otherwise refuse an unsigned manifest — and unsigned is deliberate (below).

Every path token must be RELATIVE and inside the project (the scaffold's normalisation: no `..`, no drive, no leading separator, no UNC form, no reserved device name), must carry the extension its position requires (`.csproj` for a project file, `.msix` for a package; a directory position has none), and must not be under `.pagentos/` — that folder is the companion's own inside a project, and a `-o` or a `/d` pointing at it would have a build write over the log recording it. The child's working directory is the project folder, so nothing has to be absolute for the toolchain to find it, and nothing absolute is ever accepted, which is what keeps the owner's own `.csproj` and the owner's own Desktop out of reach before a process exists. An extra token, a missing one, an MSBuild property (`-p:PreBuildEvent=…`, which is a command line a caller composed by another name), `msbuild`, `cmd /c`, a `dotnet` verb that is not one of the three, or any composition or quote character is `permission_denied` (detail `command_not_allowlisted`).

**The toolchain is DETECTED, in the same places the Cloud Core measures it.** `dotnet` resolves to `%ProgramFiles%\dotnet\dotnet.exe` first and only then to the companion's PATH (skipping the Store's `WindowsApps` aliases) — the Cloud Core's `stacks.py` order, and the safer one: a `dotnet.exe` planted earlier on PATH would otherwise be what "dotnet" means. `makeappx` resolves to the highest `<Program Files (x86)>\Windows Kits\10\bin\<version>\x64\makeappx.exe` and is **never** searched for on PATH. Nothing is executed to learn a version (the SDK directory name says it). A machine without one answers `dependency_unavailable` (detail `runtime_missing`, not retryable), naming where it looked.

**The device signs nothing, ever** (M28 §9, ADR-0095 decision 4). The Cloud Core deliberately produces an UNSIGNED MSIX and `app/nativefactory/packaging.py` says why: signing needs a certificate, and the owner's real signing identity is theirs. The device half is the same, held structurally rather than behaviourally — there is no run to observe, because the point is that no run exists:

- `signtool`, `certutil`, `certmgr`, `makecert`, `pvk2pfx` and `certreq` are refused **by name**, with or without `.exe`, case-blind, at manifest-parse time before anything is matched, resolved or scoped. Every other refusal says "that is not one of the shapes"; this one says "this device does not run that program at all", and it is stated separately so that widening a shape can never widen these in by accident.
- `ProjectRunner.RequireNoSigner` repeats the refusal against the RESOLVED executable and the materialised argument list, immediately before a process would exist.
- `NativeTools` walks the same Windows Kits directory that holds `signtool.exe` and has **no function that returns it**. The way to keep "the device signs nothing" true is to have no code that could hand a signer its path.
- A test scans every companion source and fails if a signer is named outside the three files that refuse one.

**The run.** Everything about the containment is §6l's: the companion's OWN child, in a Job Object configured before the process exists and checked to hold it, `KILL_ON_JOB_CLOSE`, no breakaway, `DIE_ON_UNHANDLED_EXCEPTION`, every UI restriction (`JOB_OBJECT_UILIMIT_ALL`), the scrubbed environment (every `PAGENTOS_*` and credential-shaped variable removed), the working directory the project folder, stdout and stderr to `<native root>\<slug>\.pagentos\run.log` cut at 1 MiB with the last 8 KiB kept, one of the 2 run slots, `already_running` / `projects_busy` as before, and `project.stop` ending only that job. What differs is the **bounds**:

| bound | value | why |
|---|---|---|
| wall clock | **20 min** | the Cloud Core's own `BUILD_TIMEOUT_S` (`app/nativefactory/service.py`), read by a test rather than restated: a device bound shorter would kill a build the Cloud Core is still waiting on, a longer one would have the Cloud Core give up on a build still running |
| job memory | **4 GiB** | a compiler with a Roslyn server and NuGet is not small |
| processes in the job | **64** | MSBuild forks a node per core and adds VBCSCompiler, NuGet and the SDK's resolvers — still a fixed, small cap, never a fork bomb |
| job CPU time | **20 min × this machine's processor count** (clamped to 1…64 cores) | see below |

The CPU bound is the one bound in this agent that is **not** the wall-clock bound, and the reason is worth stating: `JOB_OBJECT_LIMIT_JOB_TIME` terminates the whole job when the SUM of its processes' user time passes the limit, and MSBuild compiles in parallel. On an eight-core machine an honest fifteen-minute build burns two hours of user time, so a CPU bound set to the wall bound would kill honest builds and call it a limit — an assertion that is true of every run, which is the failure shape this repository has been burned by before. The wall clock is the real bound (the runner ends the job at 20 min and answers `timeout`, retryable, with the tail); the CPU bound is what that wall clock could legitimately consume on this machine.

A batch run binds no port, so nothing is probed: **`project.run` waits for the exit** (bounded by the 20 min limit and by what is left of the command's budget) and answers `{project_id, slug, runtime: "dotnet" | "makeappx", command_key, batch: true, exit_code, seconds, log_tail, log_truncated, log_path, pid}` — no `url`, no `port`. A failed compile is an EXIT CODE and a log tail, never an exception and never a success: the Cloud Core's lifecycle is what decides what a non-zero exit means, and it can only do that if the device hands it the compiler's own output.

**`project.test`'s bound follows the runtime.** It was a flat 5 minutes. A `dotnet test` restores, compiles and only then runs, which five minutes does not reliably hold, so a test command's bound is now the bound of the runtime the manifest named: 20 min for `dotnet`, unchanged 5 min for `node` and the rest — a node runner that has not finished in five minutes has not failed in a way twenty more would fix. The service's ceilings move with it: **`project.run` and `project.test` are both capped at 20 min 30 s** (was 10 min 30 s and 5 min 30 s). A web run still answers within its 20 s port wait and a node test still times out at its own 5 min — the cap is a ceiling, not a wait, and the companion is what decides which bound applies. `project.scaffold`, `project.status` and `project.stop` are still 30 s.

**Error classes.** Nothing new: `validation_error`, `permission_denied` (`command_not_allowlisted`), `not_found`, `dependency_unavailable` (`runtime_missing`, `already_running`, `projects_busy`, `tests_busy`), `postcondition_failed`, `timeout`, `cancelled`. Every result passes the browser family's forbidden-key scan (§6i) like every other result.

**Audit and log.** The same one `project_request` row per request — capability, outcome class, `duration_ms`, never a path, never file text, never a log line. The companion's startup log names the native root, the bounds, the CPU bound with the core count it was derived from, which tools were detected, and that it signs nothing — before anything is asked of any of it.

Configuration (all `PAGENTOS_AGENT_`-prefixed): companion `ProjectsRootNative` (empty = `<ProjectsRoot>\native`); the gate is `OperatorEnabled` on both halves, as for §6i, §6j, §6l and §6m.

The lab (`tests/PagentOS.Agent.Tests/Native/`) works under `%TEMP%\pagentos-operator-fixture\native\<run-id>\Projects\native` with the real dispatcher and the REAL toolchain (a test that needs one skips with the reason when the machine lacks it, so a runner without the SDK still runs the allowlist, root, bounds and signing tests): the four shapes admitted and stored as argument lists, with the ports absent and the batch flag set; 35 hostile variants refused before any process, with a counting seam in place of `Process.Start` proving the count stays 0 — another program, a shell, an MSBuild property, a Debug configuration, a foreign RID, an absolute path, a `..`, a `.pagentos/` output, a wrong extension, an extra and a missing token, and each signing tool by name; the web runtimes refused under the native root and the native shapes refused under the other two; build-in-test and test-in-run refused; a marker edited into a hostile command refused at RUN time with nothing started; the job's 4 GiB, 64 processes, kill-on-close, no breakaway and every UI restriction read back from the KERNEL, and the CPU bound proved to exceed the wall bound on a multi-core machine; a run ended by its job at a 2 s lab seam answering `timeout`; the real `dotnet build`, `dotnet test` and `dotnet publish -r win-x64 --self-contained` through `project.run` / `project.test`, producing an EXE whose MZ header and size are read back by the test rather than claimed, inside the project folder inside the native root; a deliberately broken source reporting the compiler's own `CS…` diagnostic as an exit code and a tail rather than as a verdict; the real `makeappx pack` producing an `.msix` the test opens as a zip, finding `AppxManifest.xml` and NO `AppxSignature.p7x`; and the cross-half tests that read `app/nativefactory/roots.py` and `service.py` for the root name and the build bound.

## 8. Broker REST surface (owner API)

Since M9 every endpoint below requires `Authorization: Bearer <owner-session-token>` (ADR-0027) except `POST /enroll`, which is authenticated by the owner-minted enrollment token.

- `POST /v1/devices/enrollment-tokens` → one-time token (owner session + loopback peer)
- `POST /v1/devices/enroll` (enrollment token only — see §2)
- `GET /v1/devices` — includes `status: online|offline|revoked`, `presence: online|stale|offline`, `last_seen_at`, and the **canonical device identity** (`app.devices.types.DEVICE_IDENTITY_KEYS`) at the TOP of each row: `device_id`, `presence`, `software_version`, `capabilities`, `capability_count`, `last_seen_at`. `software_version` is the value the agent announced in its last `hello` (§4) — `null`, never `""`, when no agent has ever connected. The same value is repeated inside `health` for the Cockpit; there is one value, in two readable places, never two values.

  This is a contract, not a convenience: the Windows installer's staged-update verifier decides whether a promoted candidate lives or is rolled back by reading `software_version` off this row. On 2026-09-08 that key did not exist here, the verifier read `""` for a live and correct 0.6.0 candidate, and a healthy release was rolled back after 92.6 s. `services/api/tests/unit/test_device_identity_contract.py` now holds this row's shape and the verifier's reader against each other, in both directions.
- `POST /v1/devices/{device_id}/commands` `{capability, payload, idempotency_key?, timeout_s?}` → `202 {command_id,status}` (immediately durable; never long-polls execution)
- `GET /v1/devices/{device_id}/commands/{command_id}` → full status/result/error
- `POST /v1/devices/{device_id}/commands/{command_id}/cancel`
- `POST /v1/devices/{device_id}/revoke`

  **`build_id` and `source_revision` (ADR-0118, added 2026-09-11).** Both are OPTIONAL on the `hello` and nullable on the row, so an agent built before this change still handshakes. `build_id` is what the build IS — 16 hex characters the agent derives from its own `PagentOS.*` assemblies, so it changes by construction and cannot be forgotten at release time; `"unknown"` means the agent could not read its own files. `source_revision` is the commit the SDK stamped, for a human to find the source; it is never compared.

  They exist because `software_version` is a PRODUCT version and is meant to stay still across builds: on 2026-09-11 the deployed agent announced `0.6.0` (the M25 number) while advertising the full 85-capability M28 manifest, so two different builds were indistinguishable to the one comparison that decides a rollback. The verifier's `-ExpectedBuildId` is now the deciding check when supplied, with the product version kept as a necessary-but-not-sufficient one; a row carrying no identity, or `"unknown"`, is never a match. Like `software_version`, `build_id` is readable at the TOP of the row and repeated inside `health` — one value, two readable places, never two values. Every `hello` overwrites both, **including with `null`**: a rollback to an older agent must clear the identity, because a stale one reads as "the candidate is live".

## 9. Windows agent process architecture

- **Device Service** (background; Windows Service-capable, Session 0): owns the keypair, the WS connection, idempotency store, local audit log, and machine-level capabilities. Never touches the interactive desktop.
- **Session Companion** (runs in the owner's interactive session): executes every interactive capability — `desktop.open_application`, `desktop.open_artifact`, the `browser.*` family, since M18 `desktop.alarm_start` / `desktop.alarm_stop` (audio in the owner's session) and `desktop.display_off` (a broadcast that only reaches the owner's windows), and since M18.3 `desktop.display_wake` / `desktop.display_status` (a message-only window registered for the console display-state notifications, plus a momentary display-required request and a zero-delta pointer move), `desktop.activity_status` (a `GetLastInputInfo` tick count, which the Device Service also attaches to each heartbeat), `desktop.alarm_arm` / `desktop.alarm_disarm` (a local fallback ring persisted in the owner's profile) and `desktop.play_audio` (one bounded, digest-verified greeting on the same render path as the alarm), and since M19 the Digital Operator family (§6i: windows, keyboard and pointer under the focus guard, UI Automation, screen capture, files inside the authorised roots and the allowlisted headless terminal — behind `OperatorEnabled`), and since M20 the documents family (§6j: search, locate, inspect, read, compare and extract inside the same roots — read-only, behind the same flag; since M22 also `file.fetch`, §6k: a Cloud Core render from the dialled origin into the Downloads root, the origin told to the companion in the pipe challenge), and since M23 the projects family (§6l: source written into the one Projects root, a run as the companion's own child in a bounded Windows Job Object that dies with it, its tests in the same bounds — behind the same flag), and since M25 the two 3D runtimes and `scene.inspect` (§6m: Blender headless and Unity in batch mode as bounded batch children under the 3D root only, and the tool's own read-back with its render hash-checked — behind the same flag), and since M28 the four native build shapes (§6n: `dotnet build|test|publish` and `makeappx pack` as bounded batch children under the `native` root only, no new capability name and nothing signed — behind the same flag) — and connects to the Device Service over an authenticated local named pipe. Every one of those needs the owner's session: a Session-0 process has no display to observe, no input to time, no render endpoint and no window a broadcast can reach. If no companion is connected, interactive commands fail fast with `dependency_unavailable` (`retryable: true`), and the heartbeat simply carries no `status`.
- In development both run as console processes; installing the service (requires UAC) is an owner action recorded in `OWNER_ACTIONS_MINIMAL.md`.
