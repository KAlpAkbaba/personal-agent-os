M4 review at HEAD `2304b93` (services/api/app/voice, app/narration, alembic 0004_voice, evals/voice). No Critical. One High (new, design-level, not yet live-exploitable), rest Medium/Low/clean.

**Findings:**
1. High — `services/api/app/voice/routes.py` `VerifyRequest` (lines ~122-129) and `verify_speaker_route` (159-188): the `device_trusted: bool` "second factor" required by `verify_speaker()` (app/voice/speaker.py, correctly caps an untrusted device at UNCERTAIN — unit/integration tested) is accepted **verbatim from the HTTP request body** with no binding to any real device/session identity (no broker/device-registry cross-check, no signed assertion). `VerifyRequest.owner_accept`/`not_owner_max` are also fully caller-overridable per call. Compounding: `POST /v1/voice/speaker/enroll` (routes.py ~131-156) always upserts the single `label="owner"` `SpeakerProfile` row with **no prior-owner confirmation step** — any caller can re-enroll (overwrite) the owner's voice profile from scratch. Net effect: anyone who can reach the API can (a) POST new `sample_embeddings` to become "the owner" profile, then (b) POST `verify` with `device_trusted: true` and get `OWNER` back — the "voice never sole secret / device trust required" invariant (constitution + VOICE_SPEC §10 + SECURITY_MODEL.md §2) holds only inside the pure `verify_speaker()` function, not end-to-end through the REST surface. Not yet exploitable for a real privileged action — nothing in the repo currently gates an authorization decision on this endpoint's output (confirmed via repo-wide grep, only voice module + tests reference it), and there is no per-request API auth anywhere in this API (pre-existing, not M4-specific). Must be fixed before any real action (or the eventual realtime/command pipeline) is gated on speaker verification: derive `device_trusted` server-side from actual enrolled-device/broker session state, never a client-supplied boolean; drop or restrict the per-call threshold override; consider requiring an existing-owner-authenticated step (or at minimum an explicit owner confirmation loop) before overwriting the enrolled profile.
2. Low — `services/api/alembic/versions/20260831_0004_voice.py` defines `_SPEAKER_DECISIONS`/`_in_list` (lines 26-31) as if a CHECK constraint enforces OWNER/NOT_OWNER/UNCERTAIN, but neither is ever applied to any column — dead code, and the decision itself isn't persisted anywhere so this is harmless today, but is a documentation/implementation mismatch worth cleaning up before a future migration assumes it's enforced.
3. Low — `services/api/app/narration/routes.py` `UpdateCursorRequest.state: str | None` (PATCH `/v1/narration/sessions/{id}/cursor`) and `service.update_cursor` write the string straight to `narration_sessions.state` (String(32), no DB CHECK, `app/narration/models.py`) with no validation against `NARRATION_STATES`. A bad value later crashes `commands.State(row.state)` in `_unpack_state` (routes.py ~85) with an unhandled `ValueError` → generic 500, breaking that session's `/command` endpoint until corrected. Single-owner blast radius (own session only), no info leak (FastAPI debug=False, no stack trace surfaced), but worth an enum/Literal validator.
4. Low — inconsistent input bounds: `CommandRequest.utterance` (narration/routes.py) and `EnrollRequest.sample_embeddings` / `VerifyRequest.probe_embedding` (voice/routes.py) have no `max_length`, unlike sibling endpoints that do cap (`PreviewRequest.text` ≤20000, `UpsertPronunciationRequest` fields ≤256/512). Not independently critical (no auth boundary regardless) but should be capped for DoS hygiene/consistency.

**Confirmed clean:**
- No raw audio ever persisted: `EnrollRequest` takes float `sample_embeddings` only; TTS/STT `audio: bytes` stays in-memory/ephemeral (benchmark report stores only length/duration/format, never the bytes themselves).
- Encrypted derived profile: `ProfileCipher` (Fernet, key = SHA-256(`voice_profile_secret`)) encrypts the JSON-serialized `OwnerProfile` before `store.put`; DB (`speaker_profiles.embedding_ref`) holds only the object key. Round-trip + "ciphertext contains no plaintext marker" + "wrong secret → VoiceError, not silent garbage" all integration-tested (`tests/integration/test_voice_persistence.py`).
- `voice_profile_secret` dev default (`pagentos-dev-voice-profile-secret`) is the same class as the pre-existing MinIO dev default (`minioadmin`) — no new pattern, consistent with M0-M3 precedent, not independently flagged.
- Real TTS/STT adapters (ElevenLabs/Azure/OpenAI/Faster-Whisper): inert without a key (`PROVIDER_AUTH_MISSING`, zero I/O) — verified by dedicated tests; API keys travel only in headers (`xi-api-key`/`Authorization`/`Ocp-Apim-Subscription-Key`), never interpolated into URLs or error-message text, so no key leakage via logs/HTTP error bodies (`_send()`'s exception messages only include `type(exc).__name__` + exc text, no header dump).
- HTTP mocking genuinely offline: `test_voice_providers.py` monkeypatches `httpx.Client`/uses `httpx.MockTransport`; no real network call reachable in the suite.
- Normalizer regex pipeline (`app/narration/normalizer.py`, ~20 ordered patterns) reviewed for ReDoS: no nested/overlapping quantifiers, all patterns linear; pronunciation-dict substitution alternation uses `re.escape`d literal tokens (no regex injection from owner-entered `token`s).
- Command parser (`app/narration/commands.py`) is a pure text→enum mapper over a fixed `Command` set; "dur" checked first and always wins (tested); `speed` clamped to [0.5, 3.0] in `apply()`; no path from crafted utterance text to an unintended state transition beyond the documented machine.
- Object-store keys for speaker profiles + benchmark reports are derived entirely server-side (Settings prefix + fixed suffix/kind, never client input) and every store op is wrapped in `validate_object_key` (`app/object_store.py`).
- Migration 0004_voice is cleanly reversible (`downgrade()` drops exactly the 4 new tables); no raw-audio columns; reasonable constraints (`uq_pronunciation_token_context`, indices on `artifact_id`/`token`).
- Repo-wide since M3 (`528583f`/`4ac3d92`/`78ca842`): no new tracked secrets, no non-loopback binds, CI workflow (`.github/workflows/ci.yml`) untouched by the M4 commits (confirmed via `git show --stat`).

**Constitution enforcement note:** "no raw audio" and "encrypted derived profile" (§7/§9 privacy) are genuinely enforced in code today. "Voice never the sole secret" is enforced only inside the pure `verify_speaker()` function — see High finding #1 above; the REST wiring that would make this true end-to-end (real device-trust derivation, protected re-enrollment) does not exist yet. Flag this again at whichever milestone first wires speaker verification to an actual privileged action.
