M20 track A (2026-09-08, branch `m20-device`, worktree `E:\AI\pagentos-wt-m20-device`) put the documents family in `PagentOS.SessionCompanion/Documents/` with its lab in `tests/PagentOS.Agent.Tests/Documents/` (54 tests after the security fixes; all nine fixtures match `expected/*.extract.json` through the real dispatcher; the whole project is 529 tests, ~31 s).

Facts that are NOT obvious from the code and cost time:
- The taxonomy had no `not_found`; spec §2 names it, so it was added with `unsupported_format` to ProtocolConstants, the schema and `frames.py` (ADR-0083 addendum 1). The spec's `invalid_argument` is `validation_error` - do not mint a second name. Cloud Core (track B) should map exactly these. The `unsupported_format` DETAILS are `too_large | not_text | unknown_kind | parse_failed | decompression_bound | page_bound` (the last two from the security fixes, addendum 3).
- `file.search` records carry no `sha256` (a search never opens a file); single-file capabilities hash under 8 MiB. Secret-bearing names are not even LISTED by a search, and since addendum 3 a secret-bearing NAME is refused lexically before any lookup (present or absent, inside or outside a root).
- Both families (operator 32 + documents 6) are advertised by the ONE `OperatorEnabled` flag; `Compose(..., operatorEnabled: true)` appends documents after operator. The M19 advertisement test's `TakeLast(Operator.Count)` had to become `TakeLast(38).Take(32)`.
- The fixture folder `services/api/tests/fixtures/documents/` contains a `.gitattributes` (LF pin); the lab must not copy it or a `*` search counts 10 files, not 9. `expected/` and `truth.json` stay in the repo.
- PdfPig 0.1.16 is one package that ships `UglyToad.PdfPig.DocumentLayoutAnalysis.dll` (`ContentOrderTextExtractor.GetText(page, false)` gives Turkish text with spaces). DocumentFormat.OpenXml 3.5.1: `CellValues`/`PlaceholderValues` compare with `==`; `PackageProperties.Title` carries the generator's title.
- **Decompression bombs (the review's High, verified live: a 2 MiB .docx -> 3.5 GiB and OOM in 3 s).** The Open XML SDK materialises a part's whole DOM in one synchronous getter, so the only place to bound it is BEFORE the SDK: `ContainerGuard` reads the zip's central directory (`ZipArchive`, `entry.Length`/`CompressedLength`, nothing inflated) in the dispatcher (`RequireBoundedContainer`, also for BOTH sides of compare before either is extracted - compare extracts A before B, and a counting-extractor test sees 1 call otherwise). PdfPig is different: `ParsingOptions.FilterProvider` is the ONE seam every inflation (xref stream, object streams, page content, fonts) goes through; `DefaultFilterProvider.Instance` is a public static FIELD; `NumberOfPages` costs zero decodes; an exception thrown from a filter propagates out of `GetPage` (lenient parsing does not swallow it) - all verified live. `BoundedFilterProvider` wraps Flate/LZW/RunLength with streaming length counts. Caps live in `DocumentBounds`.
- Test-side LZW encoder (to validate the counter against PdfPig's `LzwFilter`): the decoder lags one table entry, so the encoder's width grows when `next + earlyChange - 1 >= 1 << width`, and after the final code bump `next` once before choosing EOD's width; get it wrong and PdfPig throws `KeyNotFoundException` on a garbage code - PdfPig is the oracle.
- Memory gauges in the parallel xunit process: `Process.WorkingSet64` is two-way noisy (a 16 MiB assertion failed in the full run and passed alone); `GC.GetTotalAllocatedBytes(precise: true)` is monotonic, so the MIN over 3 attempts is a sound upper bound on the measured work - report WS, assert on allocated (`BombFixtures.Measure`). Bomb fixtures are written through streams in 1 MiB chunks; a 200 MiB run of one byte deflates to ~200 KB.
- `BrowserWorkerHostTests.A_worker_that_stops_answering_pings_is_killed_and_replaced` is load-sensitive (100 ms ping interval, exact restart count): failed once beside a 40 MiB file write, passed on rerun.
- `System.Text.Json` writes 1.0 as 1; the JSON extractor writes numbers with `WriteRawValue(GetRawText())` to match the generator's `1.0`.
- The worktree isolation guard refuses Bash heredocs, `mkdir && cd && cat` chains and multi-`&&` chains touching another worktree; the Write tool creates scratch projects fine; PowerShell `git -C <m20 worktree> <cmd>` works. PS 5.1 cannot reflect over net8 assemblies - use a scratch console project under the scratchpad (with its own NuGet.config pointing at nuget.org).
- `dotnet package search X --exact-match` needs `--source https://api.nuget.org/v3/index.json` outside the windows-agent folder.
- `state/BUILD_STATE.json` has no per-milestone M20 node (only `current_milestone`); device-side findings were recorded in ADR-0083 addendum 3, spec §2 and DEVICE_PROTOCOL.md §6j instead.

**Why:** each of these produced a red gate, an OOM, or a wrong assumption the first time.
**How to apply:** when track B / the integrator wires Cloud Core to the device, read `DEVICE_PROTOCOL.md` §6j first (the bounds and the two new details); when extending the lab, keep the oracle in the repo and the copies under `%TEMP%\pagentos-operator-fixture\documents\<run-id>`; when adding a parser, bound its input BEFORE entering it and prove it with a counting extractor plus the allocated-bytes gauge.
