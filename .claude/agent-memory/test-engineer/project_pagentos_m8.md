M8 (Authorized Asset Registry + defensive security agent) independently verified 2026-09-01 for PersonalAgentOS_Claude_Autonomous_Build_Package_v1. Verdict: PARTIAL, not closeable yet, despite excellent code quality on the parts that were actually delivered.

**What held up (do not re-litigate lightly next time):** `app/security/scope.py`'s fail-safe classification is genuinely adversarially hardened. I drove it with my own fixtures (10.20.30.0/24 CIDR + example.test domain, not the repo's canned fixtures) and every spoof I could construct was refused: string-prefix CIDR lookalikes (10.20.3.40), leading-zero/octal-lookalike octets (10.20.30.040, 010.020.030.040), hex-encoded IP (0x0a141e28), decimal-integer IP (168430120 - explicitly refused by a "numeric last label" guard in classify_target), IPv4-mapped IPv6 (::ffff:10.20.30.40 - refused on version mismatch against IPv4Network, not silently truncated), zone-id/percent-encoded suffixes (both raw % and %25 - charset rejects % outright), and domain suffix spoofs (evil-example.test, example.test.evil.com). Legitimate equivalences (EXAMPLE.TEST case, trailing dot, sub.example.test containment) were correctly allowed. No-DNS-resolution confirmed live: enrolling both a hostname-locator host asset and an IP-locator host asset simultaneously, an IP target only ever matches the IP asset and a hostname target only ever matches the hostname/domain asset - never crosses kinds. Lifecycle (suspended/revoked/expired/not-yet-valid) all refuse with distinct reason codes; an expired row is corrected in place (status flips, `expired` event written) on the deciding request. Ambiguity (two assets matching one target) always refuses, never silently picks. Remediation constraint gating (max_disruption ladder, per-asset remediation-class gate, apply/revert reversibility) all held under a hand-built adversarial drive. Secret hygiene held under MY OWN planted credentials (AWS-key-shaped, JWT-shaped, distinct password) run through the real Postgres+MinIO stack end to end - clean in findings, result_json, audit events, canonical artifact body, and both PDF/HTML render bytes.

**The real defect (High, confirmed against the actual committed state, commits `4097b90`/`9a40daa`/`fa2c5a1`/`741e4c9`):** `app/security/provider.py::RegistryAuthorizationProvider` is correctly built and unit-tested in isolation but was **never wired into the live evolution pipeline**. `app/main.py` constructs `EvolutionRuntime(settings)` and `SecurityRuntime(settings)` as fully independent objects with zero cross-reference; `EvolutionRuntime.authorization` returned only `NullAuthorizationProvider`/env-var `StaticAuthorizationProvider`, never the registry-backed one. `git show fa2c5a1 --stat` proves the M8 commit touched only `app/security/**` and fixtures - never `app/evolution/runtime.py`/`review.py`/`routes.py`. So ADR-0026's claim ("this registry is also the verification source the M7 evolution permission model already depends on") and the M8 commit message's claim ("provider: RegistryAuthorizationProvider closes the M7 gap") were false of the running committed system. **Lesson: when a milestone claims to close a prior milestone's gap by adding a new class that satisfies an existing Protocol/interface, always grep for where the interface's *consumer* actually constructs its implementation (here: `EvolutionRuntime.authorization` / `app.main.create_app`) - a correct, tested, protocol-conforming class that nothing calls is exactly the kind of gap that "both modules have 100% passing unit tests" hides.**

**Unusual and worth flagging to the user every time it recurs:** mid-verification, a concurrent `security-reviewer` session was independently reviewing the same M8 code in the SAME working tree (not an isolated worktree) and found the identical High finding plus a real Medium (`app/security/checks.py::collect_files` used `Path.is_symlink()` for containment, which does not detect a Windows NTFS junction - `IO_REPARSE_TAG_MOUNT_POINT` vs `IO_REPARSE_TAG_SYMLINK` - so a junction inside an authorized config root could walk the collector outside it). That session then **directly patched product source uncommitted** (`evolution/runtime.py`, `security/checks.py`, `security/registry.py` + ~25 new tests) while I was reading/testing the same files - confirmed via `git status`/`git diff` showing files I had already Read cleanly turn up modified minutes later, and file mtimes matching. This is a reviewer role modifying source directly rather than reporting findings for the owning engineer to fix - itself a process deviation from CLAUDE.md's mandated pipeline (tests-first -> implement -> gate -> independent review -> record decision -> commit), since the patch landed with no commit, no ADR update, and (until it caught up mid-session) no tests. **How to apply: when verifying in a shared (non-worktree) working directory, always re-run `git status`/`git diff --stat` immediately before writing the final verdict, not just at the start - the tree can move under you. Score the milestone against the last real commit, not against whatever the working tree happens to contain at verdict time; report live drift as a caveat rather than silently absorbing it into the verdict.**

**Also confirms the M6 finding generalizes:** `state/BUILD_STATE.json` still read `current_milestone: M8, status: NOT_STARTED, last_completed_milestone: M7` at verification time despite 4 real M8 commits on main - `quality-gate.ps1` does not touch this file. Always check it explicitly; never infer milestone-closed status from git log/docs alone. See [[project-pagentos-m6]] for the first occurrence of this same gotcha.
