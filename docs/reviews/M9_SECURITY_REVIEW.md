# M9 Security Review — 2026-09-01

Independent review of the owner identity layer (ADR-0027): bearer sessions with a file-backed credential root, the host-side recovery CLI, `require_owner_session`/`require_scope` applied across every module M4–M8 had left on the standing API-auth hard gate, plus the mobile/web sign-in surface and the artifact-ready push announcer.

**No Critical, no High. Two Medium and three Low, all fixed.** The reviewer additionally ran the route-table sweep test that walks the live FastAPI dependency graph and confirmed the unauthenticated surface is exactly the five documented endpoints (health, `POST /v1/identity/bootstrap`, `POST /v1/identity/sessions`, `POST /v1/devices/enroll`, `WS /v1/devices/connect`) — each with its own credential, none open.

## Findings and dispositions

| # | Severity | Finding | Disposition |
|---|---|---|---|
| 1 | Medium | `mobile/announcer.py::_claim()` committed `tasks.announced_at` **before** the notifier ran. A crash or a provider failure between the two permanently dropped that task's notification — and migration 0010's own docstring claimed the opposite ("an API restart mid-delivery retries rather than loses it… exactly-once per task"). | **Fixed**: one transaction now spans the whole pass — select `FOR UPDATE SKIP LOCKED`, deliver while still holding the row locks, stamp only what was delivered, commit. A failed delivery leaves that task unannounced for the next sweep; a crash rolls the pass back entirely; a concurrent API process skips locked rows instead of announcing them twice; a READY task with no artifact is still stamped so it is not re-examined forever. The first attempt at this fix split select and stamp into two sessions, which released the claim before delivery and re-introduced a double-announce window — caught on re-read and corrected. The migration docstring now states at-least-once with collapse-key idempotency, which is what the code does. Three regression tests pin the ordering: failed delivery, partial-batch failure, and crash-mid-sweep. |
| 2 | Medium | `require_scope()` — ADR-0027's "scopes narrow, never elevate" — was implemented and unit-tested but wired into **zero** shipped routes; every module gated on bare `require_owner_session`. A scoped session therefore had full owner authority in practice. Same defect class as M8 finding #1 (`RegistryAuthorizationProvider` never wired). | **Fixed structurally, not by remembering to use the right dependency**: bare `require_owner_session` now **refuses** any session carrying scopes (403, audited as `scope_missing:<unrestricted>`), so a scoped session can only ever reach a route that explicitly declares a scope. `require_scope` depends on a new authentication-only dependency and keeps accepting both a matching scoped session and an unrestricted one. Today no route declares a scope, so a scoped session reaches nothing — the safe direction, and it can no longer become unsafe by omission. |
| 3 | Low | `_require_loopback` (duplicated in `identity/routes.py` and `broker/routes.py`) failed **open** when `request.client is None` — the transport being unable to identify the peer is not evidence of loopback. | **Fixed** in both: `if host not in _LOOPBACK_HOSTS: raise`. Bootstrap mints owner authority from nothing; it is the last place to be permissive about who is asking. |
| 4 | Low | Device revocation and its session revocation are two independent transactions (two runtimes, two engines) with nothing reconciling a crash between them. | **Fixed by ordering**, since atomicity is not available here: sessions are revoked **first**, the device row second. The surviving failure mode is now "the revoke did not take effect, retry it" (device still enrolled and visible, revoke is idempotent) instead of "device revoked but its bearer token still works". An integration test simulates the crash and asserts both halves. |
| 5 | Low | A **corrupt** (not missing) identity root failed closed as designed, but surfaced as an unhandled 500 rather than a refusal. | **Fixed, and the security half with it**: a typed `CorruptIdentityRoot` maps to the same coarse 401 as every other exchange refusal (audited as `identity_root_unreadable`), and `POST /bootstrap` returns 409 pointing at host recovery. Critically, bootstrap must never read "unreadable" as "absent" — otherwise damaging the file would be a path to seizing ownership. A test asserts the damaged root is not overwritten. |

## Explicit verdicts (post-fix)

- **Is there an authentication bypass? No.** The unauthenticated surface is the five documented endpoints and is enforced by a test that walks the real route table and dependency graph, so a new unprotected route fails the suite rather than shipping quietly.
- **Is M4–M8's standing hard gate closed? Yes for authenticate-or-refuse.** Every memory, voice/narration, self-healing, evolution, security and broker endpoint now requires an owner session. The finer scope narrowing the ADR describes is enforced but not yet load-bearing, because no route declares a scope — now failing closed rather than open (finding #2).
- **Does device revocation actually end the device's authority? Yes**, on one code path, and now in an order that survives a crash between its two transactions.
- **Are tokens recoverable from storage or logs? No.** Only SHA-256 hashes are stored; comparison is constant-time; the plaintext session token appears in exactly one response body and nowhere else; the audit rows are token-free by construction.

## Clean areas (verified)

The credential root is deliberately not a database table (Constitution §6): a restored or rebuilt database neither resurrects nor destroys the owner's ability to authenticate, and recovery runs on the host rather than through the API the credential protects. Root writes are atomic (write-then-`os.replace`) with owner-only permissions and inheritance-stripped Windows ACLs. Refusals are coarse to the caller (`unauthorized`/`forbidden`/`throttled`) and precise in `session_events`, so a stolen credential gets no oracle. Failed attempts are throttled and the rejection audit is itself bounded so it cannot be used to flood the table. There is **no test-only authentication bypass** anywhere in the suite: every test holds a real token minted by the real service, which is what makes the suite evidence that the endpoints are protected.

## Recurring lessons reconfirmed

1. *A component built and unit-tested but never wired into the real routes changes nothing* — M8 (authorization provider), M9 (`require_scope`). Both fixes now assert the wiring, not the class.
2. *A docstring's durability or atomicity guarantee is a claim to verify against the actual commit ordering* — finding #1 promised exactly-once while the code stamped before delivering.
